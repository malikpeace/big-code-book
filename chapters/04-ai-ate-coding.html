How AI ate coding, and what is actually true in 2026

Five years took coding from autocomplete to agents that work unattended for hours. The capability is real, the receipts are mixed, and almost everything written about it is one of three very different kinds of claim. Here is how to tell them apart, and the five habits that keep your app alive.

LAST TIME

Every layer under Memento is old: JavaScript from 1995, Git from 2005, npm from 2010, TypeScript from 2012, React Native from 2015, Supabase from 2020. Each one is an abstraction, a hard job done once and wrapped in a name. Abstractions leak, so when something makes no sense at your layer, look one floor down.

Quick check

What is a compiler, in one sentence?
A program that turns human-readable code into instructions the machine can run. Fortran, 1957. It is the move the whole history repeats: do the horrible job once, wrap it, never do it again.
Memento's web app has no bundler. What does a human have to do by hand because of that?
Keep the script load order correct in index.html, and type the ?v= version on each file when it changes so browsers do not serve a stale copy.
Does Memento touch SQL? Swift? Python?
SQL yes, 33 migration files on Supabase. Swift only underneath React Native, never written by anyone on your side. Python yes in the repo, 10 tracked files of tooling, mockup and build scripts plus a legacy backend file, but none of it in the shipped web or native clients.

The idea

Three kinds of sentence get printed about AI and coding, and they look identical on a screen. Mixing them up is why founders lurch between "it can do everything" and "it is all fake".

  1. Release facts. A thing shipped on a date. Checkable. Boring. True.
  2. Vendor benchmark claims. A company reporting its own score on a test it chose, run on a setup it built. Not lies, but marketing until somebody else reproduces them.
  3. Independent evidence. Controlled studies, code-quality measurements, payroll data, and incidents that actually happened to real companies. Slower, less flattering, and the only category that tells you what to do on Monday.

Hold those two METR numbers together, because they are the most useful pair of facts in this chapter. In 2025 the tools made people slower while feeling faster. In 2026 the same team measured a real gain. Both are true, a year apart, and the gap between what people felt and what was measured never closed. Your own sense of speed is not evidence. It never was.

The GitClear finding should worry a founder specifically. Cheap code means more code, and more code that repeats itself. That is the mechanism behind every "why does this app have two systems that do the same thing" moment you have had. Simon Willison put it best: he can produce code a hundred times faster and does not have a hundred times the capacity to stay on top of it.

One more category to recognise: numbers that exist to sell you a scanner. The claim that 8,000 of 10,000 vibe-coded startups need a $50,000 to $500,000 rebuild traces back to a security vendor with no published method, and so do most "one-person unicorn" pieces. Solo founders were 63% of new companies registered through Stripe Atlas in Q2 2026, which is real. No one-person company has been verified at unicorn scale. Treat a number with no method as an advert.

What is actually true, September 2026

Reliable: a whole feature or screen from a clear spec, with tests. Big refactors and migrations, sometimes running for hours. Scripts, data cleanup, one-off tools. Reviewing another agent's work.

Still unreliable, and every one of these has bitten your project: long-horizon consistency, because agents lose memory between sessions and return with incomplete features, duplicated work, or a declaration that the job is finished when it is not. Duplicate systems. Scope creep, where a small fix quietly grows. Hallucinated functions and files that sound exactly right and do not exist. Confident wrong claims about its own work. Security defaults, because an agent optimises for "it works", not "it is locked down". And the last 30%: edge cases, integration, and security are as hard as they ever were.

Which leaves a clean division. The agent owns typing and, increasingly, the first draft of the plan. The human owns architecture, the definition of done, verification, security posture, and product judgment. That is not a consolation prize. It is the entire job that was always underneath the typing.

The five habits, starting today

  1. Read the plan before the code. Make the agent say what it will do and which files it will touch. Wrong plans are cheap to fix, wrong code is not.
  2. Read the diff. The diff is the list of exactly which lines changed. Chapter 7 teaches you to read one. Never approve what you have not seen.
  3. Ask why, not what. One conceptual question per session. Anthropic's own study found delegating dropped comprehension sharply, while asking why preserved it. That is what the box at the end of every chapter is for.
  4. Demand a verification step. Not "it works". A test that passes, a screenshot, a command with output. Something a machine produced, not something the agent asserted.
  5. Own the commit. It goes out under your name, with your customers behind it. "The agent did it" is not a status any user has ever accepted.

See it

The difference between an agent that reports success and one that checks. Same job, two functions. Run it and read which one tells you the truth.

// The server, as it really is. Three files were expected. One never arrived. const server = { files: ["index.html", "app.js"] }; const expected = ["index.html", "app.js", "style.css"]; function claimsItWorked() { console.log("Deployed successfully. All files are in place."); return true; } function actuallyChecks(want) { const missing = want.filter(f => !server.files.includes(f)); if (missing.length > 0) { console.log("FAILED. missing:", missing.join(", ")); return false; } console.log("verified:", want.length, "of", want.length, "files present"); return true; } console.log("claim:", claimsItWorked()); console.log("check:", actuallyChecks(expected));

Both functions are honest code. One of them never looked. "Tests pass" with no output pasted is the first function. Every time.

Now in Memento

ANY APP

The fix every practitioner agrees on is not a better prompt. It is a harness: written rules the agent reads at the start of every session, because it remembers nothing from the last one. A harness is the scaffolding around the model, the files, checks and hooks that make its behaviour repeatable. Rules in a file beat rules in your head, because the file is still there at 2am when you are not.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative is to tell the agent the rules in chat each time. It works, right up until the session is long, or it is a new session, or there are two agents and only one of them was told. Memento's answer is a file every agent reads on every session, plus a log file for fixes that land during the freeze, plus a plan file that says which agent owns which folder. The cost is real: the rules have to be maintained, they get long, and a rule nobody enforces is decoration. Some of Memento's are enforced mechanically by a hook rather than by good intentions, which is the direction the whole industry moved in 2026. Rules a machine checks beat rules a model is asked to remember.

WORDS YOU NOW OWN
Agent
A model given tools, a terminal, and permission to act in a loop until a job is done. The change from 2025 onward is duration, not intelligence.
Benchmark
A standard test a model is scored on. Useful, gameable, and self-reported by whoever is selling the model.
Hallucination
A confident statement that is not true: a file that does not exist, a function never written, "tests pass" with no output.
Vibe coding
Accepting whatever the AI produces without reading it. Fine for a toy. Fatal for a product with users.
Harness
The scaffolding around an agent: rule files, plan files, checks and hooks. Memento's CLAUDE.md is one.
Diff
The exact list of lines a change added and removed. The thing you read before you approve anything.
Row Level Security
A database rule deciding which rows each user may see. Missing it is what exposed the Lovable apps and Moltbook.
Context window
How much text a model can hold at once. Opus 4.8 and Opus 5 hold about a million tokens. It still ends, and when it does, everything not written to a file is gone.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you treat the three categories as trustworthy, suspicious, and true. Independent studies age badly, as METR's own revision proves, and they measure a population that is not you. Vendor benchmarks are often directionally right. Release dates say nothing about whether the thing is any good. Real model: every claim carries a method and a date, and the questions are always the same two: who measured this, and does their setup look like mine? A solo founder with two agents on a frozen web app and a native rebuild is not the average enterprise developer in any of these studies. Use the receipts to know which failures exist, then verify your own app yourself.

RABBIT HOLE: why a benchmark saturates

SWE-bench Verified is a fixed set of real GitHub issues with real tests. Once models reach the mid-90s, the remaining failures are mostly ambiguity in the issues themselves, so the score stops separating good models from great ones and the industry moves on: SWE-bench Pro for harder tasks, Terminal-Bench for jobs needing a shell. There is also leakage: the issues are public, so a model trained on the internet may have read the fix. Every benchmark has a shelf life. When a launch quotes a benchmark you have never heard of, the famous one usually stopped flattering them.
