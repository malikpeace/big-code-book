Quick check

What is the difference between npm install and npm ci?
install may update the lockfile, so two people can end up with different versions. ci deletes what is there and installs exactly what the lockfile says. Robots and labs use ci: reproducible beats convenient.
In React, what is a component?
A function that takes props and state and returns a description of what to draw. It does not touch the screen itself. It returns a description, and the framework works out what to change.
What does "build" mean, as opposed to "run"?
Build turns source into something executable: compiled, bundled, packaged. Run is executing the result. The web Memento has almost no build, which is why a push deploys in seconds. Native has a real one, which is why tonight takes a while.

The idea

An app on an iPhone is one installed thing, so it feels like one lump. While it is being built, it is two.

The first part is the native shell: real compiled code, packaged into the thing iOS installs. It owns the window, the fonts, the keyboard, the secure storage. Building it needs Xcode and takes minutes.

The second part is the JavaScript. Every screen and every piece of logic you have been reading in src/ is TypeScript, which becomes JavaScript, and it is not compiled into the shell. It is loaded when the app starts, like a web page loading a script.

That split is the whole trick. Build the shell once, then change the JavaScript all day and the app reloads in a second. The shell that does this is a dev build: a normal native app with one extra ability, which is to fetch its JavaScript from your Mac instead of carrying its own copy.

The program on your Mac that serves it is Metro, React Native's bundler. It reads the entry file, follows every import, glues the graph into one big JavaScript file, hands it over on request, then watches your files. Save one, Metro rebuilds what changed and pushes it, and the running app swaps the new code in without restarting. That is Fast Refresh, which everyone calls hot reload.

The simulator is the fourth piece: a real copy of iOS running on your Mac, pretending to be a phone. It boots, installs apps, has a home screen. No camera, no cell radio, no App Store, and it reports safe-area insets of zero unless told otherwise. Close enough for tonight.

ANALOGY (TEMPORARY)

The dev build is a television set. Building it is manufacturing the set: slow, done once, needs a factory (Xcode). Metro is a small broadcast tower on your Mac. The television has no programming of its own, it tunes to the tower. Change the show at the tower and the picture changes immediately, with no new television. The simulator is the showroom: a fake living room on your desk.

The four commands, and what each actually does

npm ci
Reads package-lock.json and installs those exact package versions into node_modules/. Borrowed code, chapter 19. It downloads a lot and prints a lot. Nothing runs.
npm run check
Runs whatever the project defined under the name check. In Memento that is the typechecker and then the test suite. This is the same gate the robot runs on every push, so if it passes here, the code is in the state CI expects.
npx expo run:ios
The heavy one. Generates the iOS project, installs the native dependencies, compiles the shell with Xcode, boots a simulator, installs the app, starts Metro, opens the app. First time: many minutes. Afterwards the shell is already built and it is fast.
npx expo start --dev-client
Metro only. Use it once the dev build exists on the simulator. Seconds, not minutes. --dev-client means "the app that will connect is a dev build of this project", not the generic Expo Go app.

Two places talk to you. The Metro terminal prints bundle progress, every reload, and anything the app writes with console.log or console.warn. The simulator shows errors on screen with a stack trace, the kind you learned to read in chapter 23. Cmd and D with the simulator focused opens the developer menu.

Finding the file that drew a screen

Memento's native app uses expo-router: file-based routing, where the file's path is the URL. src/app/index.tsx is the screen at /; src/app/settings.tsx would be /settings. Nobody writes a route list. The folder is the list. _layout.tsx is the exception: the underscore means "not a screen", it is the wrapper the screens render into.

Which gives you a two-step way to find any screen in any React Native app. Read a word off the screen, grep for that word, and the file holding the text is the file that drew it.

See it

File-based routing in fifteen lines: a map from paths to screens, and a function that resolves a URL against it. Predict the last three lines before you run.

// expo-router, in miniature. The folder IS the route table. const files = { "src/app/index.tsx": "Home", "src/app/settings.tsx": "Settings", "src/app/notes/index.tsx": "NotesList", "src/app/notes/[id].tsx": "OneNote", "src/app/_layout.tsx": "RootLayout" // underscore: a wrapper, not a screen }; function resolve(url) { const path = url === "/" ? "index" : url.replace(/^\//, ""); for (const file in files) { if (file.startsWith("_") || file.includes("/_")) continue; // layouts are not screens const route = file.replace("src/app/", "").replace(".tsx", "").replace(/\/index$/, ""); if (route === path) return files[file] + " (from " + file + ")"; if (route.includes("[") && path.startsWith(route.split("/[")[0] + "/")) { return files[file] + " (from " + file + ", id=" + path.split("/").pop() + ")"; } } return "404: no file matches " + url; } console.log(resolve("/")); console.log(resolve("/notes/abc123")); console.log(resolve("/billing"));

The real router is more careful, but the shape is honest: no route table, only a folder, and a missing screen is a missing file.

ANY APP

A project's package.json has a scripts block: the project's list of verbs, the commands its own authors use. Read it before you read any code, because it says how to start the thing, how to test it, and what the robot on the server runs. npm run with no name lists them all.

MEMENTO

Six verbs, and every one of them is a command from this chapter:

"scripts": {
  "start": "expo start --dev-client",
  "ios": "expo run:ios",
  "android": "expo run:android",
  "typecheck": "tsc --noEmit",
  "test": "jest --runInBand",
  "check": "npm run typecheck && npm test"
}
memento-native/package.json:9-16 (native pin 93bfa796)

check is two commands with && between them, meaning "and only if that succeeded". Typecheck first, fast and catches the stupid things; tests second. --runInBand runs the test files one at a time instead of in parallel: slower, far easier to read.

What boots first

Two files decide what you see. The router wraps the matched screen in _layout.tsx, so the layout is first:

export default function RootLayout() {
  const [loaded, error] = useFonts({
    GeistRegular: require('../../assets/fonts/geist-400.otf'),
    GeistMedium: require('../../assets/fonts/geist-500.otf'),
    GeistBold: require('../../assets/fonts/geist-700.otf'),
  });
  ...
  if (!loaded && !error) return null;
  return (
    <AppFontsReady.Provider value={loaded && !error}>
      <StatusBar style="light" />
      <Stack screenOptions={{ headerShown: false, contentStyle: { backgroundColor: '#000000' } }} />
    </AppFontsReady.Provider>
  );
}
memento-native/src/app/_layout.tsx:10-31 (native pin 93bfa796)

Read the shape, not the details. It loads three font files. While they load it returns null, which draws nothing, which is why the splash screen is still up. When they are ready it returns a black stack with no header, and <Stack /> is the hole the matched screen renders into.

Then the screen. src/app/index.tsx is 150 lines and the part that matters is the last four:

export default function Index() {
  if (ENTRY_SAMPLE) return <EntryGate open={openNativeEntryRoot} available={entryAvailable} />;
  return FEEL_SAMPLE ? <FeelSample /> : <RootGate />;
}
memento-native/src/app/index.tsx:147-150 (native pin 93bfa796)

The first screen is a three-way fork. Two branches are dev-only previews switched on by environment variables (chapter 19) and guarded by __DEV__, so a release build cannot reach them. With no flags set you get RootGate, the real boot gate, and that is why the screen may be sparse. The rebuild is mid-flight, and the README has said so since the first commit: "This is a native boot screen, not the migrated product." What RootGate renders depends on which branch of its own gate wins. Reading the source, a clean simulator with no preview flags and no saved session settles on "Sign-in is not connected yet."; a ready saved session gets BootScreen; blocked storage gets the recovery copy. Nobody has booted a real simulator to confirm that yet, so treat it as read from the code, not observed.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative to a dev build is Expo Go, a ready-made app from the App Store that loads your JavaScript with no Xcode and no build step. Memento cannot use it, because Expo Go only contains the native code Expo shipped inside it, and Memento depends on Skia for the star, MMKV for storage, Reanimated, secure-store and a gesture handler. Those are native modules. Wanting them means shipping your own shell, which means Xcode and the long first build. The other alternative is bare React Native, which hands you the same Xcode project plus every configuration file to maintain by hand. Expo with a dev build is the middle: your own shell, someone else's plumbing.

WORDS YOU NOW OWN
Native shell
The compiled part of a React Native app: the window, the fonts, the storage, the native modules. Built by Xcode, changed rarely.
Dev build
A native shell built once with one extra ability: it loads its JavaScript from a server on your Mac instead of carrying its own copy.
Bundler (upgraded)
The program that follows the imports from one entry file and produces a single file the runtime can load. Metro is React Native's.
Metro
React Native's bundler. Follows every import from the entry file, glues them into one JavaScript bundle, serves it, and watches for changes.
Fast Refresh (hot reload)
Save a file, the running app swaps in the new code without restarting and usually without losing what is on screen.
Simulator
A real copy of iOS running on your Mac, pretending to be a phone. No camera, no radio, no App Store, and it reports safe-area insets of zero unless you tell it otherwise.
expo-router
File-based routing. A file in src/app/ is a screen and its path is its URL. _layout.tsx is a wrapper, not a screen.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you think the television is dumb. The dev build runs the JavaScript itself, on the device, in its own engine, calling into real native code the whole time. Metro sends text, not pixels. It also breaks the moment you ship: a release build has no tower, because the bundle is compiled in and frozen. Real model: two artifacts with different build cycles, and one connection between them that exists only in development. The app you eventually put on the App Store carries its JavaScript inside it, and everything you did tonight is gone from it.

RABBIT HOLE: what expo prebuild actually generated

The repo has no ios/ folder. npx expo run:ios makes one from app.json: the bundle identifier co.mementoapp.foundation, the scheme memento-dev, the splash screen, the fonts, the plugin list. The Xcode project is an output, not a source, so it can be deleted and regenerated and never argued over in a diff. The cost: hand-editing it is pointless, the next prebuild overwrites you, so anything you need must be expressible as a config plugin. Those development identifiers are deliberately separate from production, and the README says not to register them as the store identity.
