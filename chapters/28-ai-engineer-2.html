The idea

The loop in chapter 27 catches wrong code. It does not catch extra code, and extra is what agents produce. GitClear measured duplicated blocks rising eightfold across 211 million changed lines in 2024, with copy-paste passing refactoring for the first time on record. Willison said it in one sentence: he can write code a hundred times faster and does not have a hundred times the capacity to stay on top of it.

Extra comes in two shapes. A duplicate system is a second thing doing a job something already does. Scope creep is a change that grew past the ask. Both are additions, both look like productivity, and both are paid for by whoever later has to work out which one is real.

Why agents do it: they do not grep first, because writing is what they are good at. They start every session with no memory, so last Tuesday's work is invisible. And adding feels safe, since a new file cannot break an existing test while changing a shared function might. Anthropic names the same failure: lost memory between sessions producing duplicated work and premature declarations of completion (anthropic.com/engineering/harness-design-long-running-apps).

Four preventions, the first one free.

  1. "Does this already exist?" opens every ask. Before what, before where. It turns a build request into a search request, and the search is cheap.
  2. Grep before build. Make the agent show the search it ran. "I did not find one" with the command pasted is an answer. Without it, a guess.
  3. One owner per file. Two agents in one file is how you get two implementations of one idea in one place.
  4. A file map that is true. An agent with an accurate map finds the existing thing. With a wrong one, it builds a new thing.

That last one is not hypothetical for you. CLAUDE.md:10 says the app has 21 JavaScript files; it has 38. 2. How scope creep happens, and the sentence that stops it

You ask for one fix. The diff has the fix, a renamed variable, a reformatted file, a new helper, and an unrelated bug the agent could not leave alone. Each is defensible alone. Together they are a change you cannot review, cannot revert in one move, and cannot explain to yourself in a week. The tells live in --stat, ten seconds of reading:

What you seeWhat it means
More files than your ask namedThe agent went somewhere you did not send it.
A file with a huge line count and no behaviour changeA reformat. It hides real edits inside noise and makes the diff unreadable.
A rename across many filesPossibly an improvement. Definitely not what you asked for, and definitely harder to revert.
A new file you did not discussDuplicate-system risk, from section 1.
A shared file in the list (js/01, js/09, css/base.css)The blast radius just went app-wide.

The guard is one sentence, and it goes at the bottom of every ask:

Change only X. If you see something else worth fixing, list it, do not fix it.

It works because it gives the agent somewhere to put the urge. The list it returns arrives as a decision for you instead of lines in a diff.

You already run the industrial version. The freeze is scope control as law: CLAUDE.md:54-55 allows bug fixes only, and only for bugs blocking a real person or a test account. Everything else is out of scope by default, for every agent, without you typing a word. A good rule moves the default.

3. Understand, or delegate

Chapter 27 cited Anthropic's February 2026 trial: the AI-assisted group scored about 17 points lower on comprehension, except for those who asked conceptual questions, who matched the hand-coders. Delegation costs understanding. Sometimes a fine trade, sometimes the trade that ends your company.

The rule of thumb: delegate typing, never delegate understanding of anything you will decide about again. You will decide about pricing again, and about your data model. You will not decide about a button's easing curve again.

Understand it firstSafe to delegate
Money: checkout, receipts, entitlement, refundsStyling, spacing, copy inside an approved voice
Auth: who is signed in, what they may doBoilerplate, wiring, repetitive edits across files
Data: what is stored, where, who can read itTests for behaviour you have already specified
Deletion: anything that removes a row or a fileBuild config, scripts, one-off tooling
Anything you will be asked about by a customerAnything you could throw away and regenerate

Money, auth, data, deletion. If a change touches one of those, you read it before it ships and you use "explain, then stop" until you can say what it does in your own words. That is the only reason the loop in chapter 27 has a human in it.

5. How to recover when it fucks up

The first move is looking, not typing. git status says what changed and whether it is staged, git diff says what those changes are, git log --oneline -5 says what is already snapshotted. Thirty seconds of reading picks which of the next four commands is right. Typing before reading is how a recoverable mess becomes a real one.

The safety commit comes first whenever anything is uncommitted. It is not a good commit and nobody will read it. Its job is turning work that can be destroyed into a snapshot with a hash, which moves you off the top row, where every option below is reversible.

git add memento-app/js/06-consistency-mori.js
git commit -m "WIP: before undoing the agent's change"

Then the four real moves.

CommandWhen
git restore --source=<commit> -- <file>One file went wrong and you want the version from a known-good commit back. The -- and the explicit filename are the point: without a target this command reaches much further than you meant.
git revert <sha>A commit is bad. Makes a new commit that undoes it. Safe after pushing, because it adds history rather than rewriting it. This is what "roll back the deploy" means.
git reflog"I lost a commit." Every position HEAD has occupied, including ones no branch points at. Find the hash, then restore or branch from it.
git switch -c rescue-<date>Before anything experimental. A branch is a label, it costs nothing, and it means the worst case is that you delete a label.
DESTRUCTIVE. NEVER YOUR FIRST MOVE

git reset --hard, git checkout -- <file>, and git clean -fd all delete uncommitted work with no undo, and reflog does not help because nothing was ever committed. If an agent proposes any of them while you have uncommitted changes, the answer is the safety commit first, every time. In Memento, where two agents share one tree, these commands can also destroy the other agent's half-finished work, which is why CLAUDE.md:73 bans git add -A for the mirror-image reason.

Now the version git cannot save you from. In July 2025 a Replit agent deleted a live production database during an explicit code freeze, then reported rollback was impossible. It was not, and dev and production were separated within days. That failure is about what an agent is able to do, which you answer before it runs.

The chart, as something you run rather than remember:

function nextCommand(s) { if (s.uncommitted) { return "SAFETY COMMIT FIRST: git add [your files] && git commit -m 'WIP'\n" + "then: git restore --source=[good sha] -- [the one file]"; } if (s.committed && !s.pushed) return "git revert [sha] (history grows, nothing is lost)"; if (s.pushed) return "git revert [sha], then git push (never force, others have it)"; if (s.lostCommit) return "git reflog, find the sha, then git switch -c rescue [sha]"; return "nothing to recover. read git log and go back to the diff."; } console.log("A:", nextCommand({ uncommitted: true })); console.log("B:", nextCommand({ committed: true, pushed: false })); console.log("C:", nextCommand({ committed: true, pushed: true })); console.log("D:", nextCommand({ lostCommit: true }));

Notice what is missing from every branch. No --hard, no clean, no checkout --. A recovery routine that cannot destroy anything is one you can run while upset, which is the only state you will ever run it in.

6. How to challenge an architectural decision

An agent proposes a structure. It sounds reasonable because it is the most common structure in the training data, which says nothing about whether it fits your app. Four questions, none needing you to know the answer first.

  1. "What is the alternative, and what does it cost?" A proposal with no alternative is a preference presented as a conclusion. Two options with costs is a decision.
  2. "What would the other agent say?" You have two. Asking one to argue the other's side surfaces the trade-off, and you can go get the real second opinion if it matters.
  3. "What is the smallest version?" Anthropic's advice on agent systems is to use the simplest thing that works and add complexity only when it pays. Same logic, one level up.
  4. "What does this couple to?" Chapter 26's question, and the one that predicts your future pain. Wired into state, auth and the router means you cannot change it alone later.

Then write it down with the date and the reason, because the reason is what evaporates. You already have the file, and per byte it is the repo's most valuable document:

- **AI backend:** Anthropic via the Supabase `ai-proxy` edge function (holds
  the key). Clarity discovery = Sonnet, synthesis = Opus, Action = Sonnet.
- **Dual-AI dev workflow:** Claude plans/reviews, Codex/GPT implements. One
  model edits at a time; git is the shared source of truth.

Two decisions, each carrying its reason. Section 1 showed the cost when a record drifts, and both stay true: a written decision beats an unwritten one, and one with no date and no owner becomes confident misinformation.

ANY APP

The answer to agents producing extra is not better prompting. It is constraints a machine enforces: tests that fail, types that refuse to compile, linters, hooks, a review gate held by somebody other than the author. Thoughtworks calls these feedback sensors for coding agents. A constraint enforced by memory is one you have already lost.

WORDS YOU NOW OWN
Duplicate system
A second thing doing a job something already does. Born from not searching first, no memory between sessions, and adding feeling safer than changing. Costs are paid by everyone who later has to work out which one is real.
Scope creep
A change that grew past the ask. Visible in --stat as more files than you named, a reformat with no behaviour change, or a shared file you did not mention.
Safety commit
A throwaway commit made before undoing anything, whose only job is turning destroyable work into a hash. Always first when anything is uncommitted.
Restore
git restore --source=<commit> -- <file>. Brings one named file back from a known-good snapshot. The explicit target is the safety.
Revert (upgraded)
The only undo that is safe after pushing, because it adds a commit instead of rewriting history. The rollback move for anything already live.
Reflog (upgraded)
Every position HEAD has occupied, including ones no branch points at. Finds a commit you thought you lost. It cannot recover work that was never committed, which is why the safety commit comes first.
Kill switch
A pre-built lever that stops a dangerous system without shipping code. POLAR_PRODUCTION_MODE=disabled stops new checkout while everything else keeps working.
Fresh-context review
A review by a session that has not seen the reasoning and must reconstruct intent from the diff. If it cannot, the change is not explaining itself. Self-review cannot replace it.

RABBIT HOLE: why "add" feels safer to an agent than "change"

Changing a shared function means reading every caller, and if one breaks, the failure appears where the agent is not looking. Adding a function next to it cannot break an existing test and reads as progress. Both end the session successfully from the agent's side; only one leaves two answers to one question. Which is why types and tests change agent behaviour more than instructions do. They make "change" cheap to verify, and therefore rational to choose.
