How the web works: client, server, HTTP, APIs, JSON

Every screen that ever showed you fresh data did the same small thing. It wrote a parcel, posted it to an address, and waited for one to come back with a three digit number stamped on the front. Learn the parts of that parcel and half of "backend" stops being a mystery.

LAST TIME

State is the app's one copy of the truth, and the screen is drawn from it. Events change state, then the screen gets updated from the new state, never edited on its own and left to drift. Memento's web app does that update imperatively, by hand; React does it declaratively, by redrawing from a description.

Quick check

Your code hits await on a network request. Does the phone freeze for those two seconds?
No. await hands the thread back. The function is parked, the browser keeps drawing and handling taps, and the parked function resumes when the reply lands. A long loop would freeze it. Waiting does not.
A user taps "done" and the streak on screen goes to 4. Where did the 4 come from?
From state. The event changed state, then the screen was updated from state. Write "4" straight onto the screen instead and the screen and the truth disagree, until the next redraw silently undoes you.
A command prints on two channels and ends with a number. Name all three.
stdout for the output, stderr for complaints, and an exit code: 0 worked, anything else did not. You are about to meet the network's version of that exit code. It has three digits.

The idea

Two computers. One asks, one answers. The asker is the client: your phone, this page, the Memento app. The answerer is the server: a program on a computer elsewhere, sitting awake, waiting. The asking is a request, the answer a response. That is the entire shape of the internet.

The rules for how those two parcels are written down are called HTTP. Not a program, not a company. An agreement about where the address goes, where your instructions go, and where the contents go, so a server written by one stranger and a phone made by another understand each other with no prior conversation.

ANALOGY (TEMPORARY)

Posting a parcel to a company's mailroom. On the front, the address: which building, which department. On the top line, what you want done: "reading copy, return it" or "please file this". Down the side, labels: what is inside, who authorised it. Then the contents. Later a parcel comes back with a three digit reference number on it that tells you, before you open anything, whether it worked, whether you addressed it wrong, or whether their building is on fire.

The address

A URL is an address with named fields, the way a postal address has a street and a city. One of Memento's real ones, taken apart:

You will type a local one in a minute: http://localhost:4321/api/sync. localhost means "this very computer", so the parcel never leaves the machine, and 4321 is a port: one computer can run several servers, and the port says which.

The verb

The address says where. The verb says what you want done. Two of them do almost all the work.

VerbMeansRule of thumb
GETGive me a copy.Changes nothing. Safe to repeat. No body.
POSTHere, take this and do something.Has a body. Repeating it usually does the thing twice.
PUTReplace what is at this address with this.Repeating it lands on the same result.
DELETERemove what is at this address.Exactly as scary as it reads.

Verb plus path is what identifies a request. GET /api/sync and POST /api/sync share an address and are two different asks. A server may answer one and refuse the other.

The headers

Headers are name and value labels on the envelope: they describe the parcel without being the parcel. Two matter today. Content-Type: application/json says "what is inside is JSON", so the server knows how to open it. Authorization carries proof of who is asking. Chapter 18 does tokens properly. For now: "who may do this" travels in a header, never in the query.

The body and JSON

The body is the contents. It can be anything, but for an API it is almost always JSON: text that looks exactly like a JavaScript object and is nothing more than that. Braces, keys in quotes, values, commas.

Two functions move between the object and the text. JSON.stringify(obj) flattens an object into a string you can post. JSON.parse(text) inflates it back into a real object. Everything on the network is text, always. JSON keeps numbers, strings, booleans, null, arrays and objects, and has no idea what a date or a function is, which is why every API sends dates as strings.

The status code

The response's first line carries a status code: the outcome in three digits, readable before you open anything. The first digit is the headline. 2 worked, 4 your parcel was wrong, 5 the server broke. The ones Memento and Memento Jr actually return:

CodePlain meaningWhere it shows up
200Fine. Here it is.Memento Jr answering GET /api/sync.
201Fine, and I made a new thing.Memento's checkout function, handing back a fresh checkout link.
400Your parcel is malformed. Sending the same one again will fail the same way.Memento Jr on unparseable JSON. Memento's proxy on a badly shaped message list.
401I do not know who you are.The secure version of Memento Jr's server with no token.
403I know who you are. You may not do this.Memento's native app reads this as "paid feature, this account is free".
404Nothing lives at that address.Memento Jr on any path it has no route for.
405Right address, wrong verb.Memento's AI proxy, which answers POST and nothing else.
409Conflict. Somebody changed this while you were holding an older copy.Memento's sync, and its plan jobs when one is already running.
413Too big. I will not even read it.Memento's proxy, on an oversized conversation.
429Too many, too fast. Slow down and try later.Memento's rate limiter, before a single cent is spent.
500I broke. Not your fault.Any server with a bug in a handler.
503I am not available right now. Come back shortly.Memento's proxy when the key is missing, or the limit database is down.

A 4 means stop and fix the request. A 5 or a 429 means the request was reasonable and retrying later might work. Code that treats every failure the same either hammers a server that just told it to stop, or gives up on something that would have worked in two seconds.

API, latency, and the two kinds of answer

Put the five parts together and you have an API: a contract. These addresses exist, they take these verbs, they want this JSON with these headers, they hand back that JSON, with these status codes. "The Anthropic API" means a document describing exactly those things.

Latency is the cost. Reading a value out of memory takes nanoseconds. A round trip to a server abroad takes a hundred milliseconds before anyone does any work, and a Clarity question takes a second or two on top because a model has to think. That gap is why chapter 12 exists. Nobody invented promises for fun.

A server answers in one of two ways. A static file is read off disk and handed over unchanged, the same bytes for everybody: Memento's index.html, its CSS, its JavaScript. A dynamic answer is computed per request by running code, and differs per caller: the AI proxy's reply. Memento Jr does both, and the next chapter shows the one line where it forks.

Box 3's last line is the honest one. 302 is a redirect, a perfectly normal code, and this function has no idea what to do with it. Every status handler has a hole like that. So the question to ask of code that talks to a server is which errors it handles, and what it does with the rest.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

Memento could have sent Clarity's conversation as a GET with the whole thing crammed into the query string. Some APIs do, and it is easier to test: you can type it in a browser. Three reasons it was never on the table. Query strings cap out in the low thousands of characters. They land in server logs, browser history and every proxy in between, so a user's answers about their life get written down in five places nobody audits. And GET promises "this changes nothing", a lie when the request spends money. So: POST, JSON body, authorisation in a header. The price is that you cannot test it by typing a URL, which is why the next twenty minutes involve curl.

WORDS YOU NOW OWN
Client / server
The one that asks and the one that answers. Your phone is a client. A program sitting awake waiting to be asked is a server.
Request / response
The parcel out and the parcel back. Each has headers and usually a body; the request adds a verb and a path, the response adds a status code.
HTTP
The agreement about where in the parcel each part goes, so strangers' computers can talk with no prior conversation.
URL
An address in named fields: scheme, host, path, and an optional query. Never a place for secrets.
Port
Which server on that computer. One machine, many programs listening, each on its own number.
Verb (method)
The intent. GET reads, POST sends, PUT replaces, DELETE removes. Verb plus path is what identifies a request.
Header
A name and value label on the envelope. Content-Type says what is inside; Authorization says who is asking.
Body
The contents. On a POST it is where the real data goes.
JSON
Text shaped like a JavaScript object. JSON.stringify flattens an object into it, JSON.parse inflates it back.
Status code
The outcome in three digits. 2xx worked, 4xx you were wrong, 5xx the server was wrong. 429 means slow down.
API
The contract: these addresses, these verbs, this JSON in, this JSON out, these status codes.
Latency
The waiting. A thousand times slower than anything else your code does, which is why async exists.
Static file vs dynamic answer
Bytes read off disk unchanged for everybody, versus a reply computed by running code for this one caller.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you picture one parcel, posted, arriving whole. A response can arrive in pieces over several seconds while the connection stays open, which is how Memento's native app streams an AI answer word by word. A parcel that comes in instalments is not a parcel. And there is no mailroom clerk remembering you between visits: every request arrives with no memory of the last one, which is why a token is re-sent on every single call. Real model: a connection opens, bytes go out in an agreed order, bytes come back, the connection closes or is reused. HTTP is stateless by design, and every "logged in" feeling you have had on the web is a token re-presented, silently, dozens of times a minute. Chapter 18 makes that concrete.

RABBIT HOLE: what the s in https actually buys you

Two things. The contents are encrypted in transit, so the coffee shop Wi-Fi sees that you talked to supabase.co and how much, but not what. And the server proves it really is that host with a certificate your device already trusts, which stops a hostile network handing you a fake. What it does not buy is safety once the parcel arrives. A perfectly encrypted request to a server with no rate limit is a perfectly encrypted disaster.
