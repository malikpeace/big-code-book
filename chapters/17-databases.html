Databases, SQL, migrations, and the trust-boundary bug

The database is the last stop on the journey and the only one that remembers. It is also the one place where a single missing rule hands every user's data to a stranger. That rule has a name, Memento has it switched on, and three of the four incidents from chapter 4 are companies that did not.

LAST TIME

A server is a program that listens on an address and runs a function for each request. A route is a function attached to an address. Memento's ai-proxy edge function is a server someone else keeps warm: it checks the origin, checks the rate limit, adds the secret key, calls Anthropic, and scrubs the error on the way back.

Quick check

What is the difference between a 401 and a 404?
401 means "I do not know who you are, and this needs a who." 404 means "there is nothing at this address." A careful server answers 404 for things that exist but are not yours, so the difference teaches an attacker nothing.
Why does the ai-proxy read the Anthropic key from the environment instead of the request?
Anything in the request came from a stranger's device, and a secret that ships to a phone is not a secret. Deno.env.get('ANTHROPIC_API_KEY') reads a value that exists only on the server.
A function returns nothing. What do you get back, and why does that bite?
undefined. It bites because the call looks like it worked and nothing throws. You find out three steps later, when something reads a property of undefined and stops.

The idea

A database is a filing system that answers questions, and everything in it lives in tables. A table is a grid. Every column has a name and a kind of value it may hold, and every row is one thing: one user, one saved state, one payment. Picture a spreadsheet.

Two rows must never be confusable, so one column is the primary key: the value that identifies that row and appears nowhere else. In Memento's user_state table it is user_id. One row per person, forever.

Tables point at each other with a foreign key: a column holding another table's primary key. The user_id in user_state also points at the auth row that is you, which is how the database knows the saved blob and the email address belong to one human.

The tables, columns, types and keys together are the schema: a promise. "Every row here has a revision, and it is a whole number." Everything downstream is written against that promise, which is why changing a schema is a bigger deal than changing code.

ANALOGY (TEMPORARY)

A filing room. Each table is a cabinet, each row a folder, each column a printed field on its cover. The primary key is the folder number, and a foreign key is that number written on another folder. The schema is the blank form the whole room agreed to use. And on the door there is a clerk who reads your badge and hands you only the folders with your name on them. That clerk is the part everybody forgets to hire.

SQL: the four sentences

SQL is the language you talk to the database in. It reads almost like English, and for reading purposes there are four sentences, here on a tiny two-table Memento.

StatementIn plain words
select email from users where id = 'u_2';Give me the email column, from the users table, only for the row whose id is u_2.
insert into user_state (user_id, revision) values ('u_2', 1);Add a new row to user_state with those two columns filled in.
update user_state set revision = revision + 1 where user_id = 'u_2';Find that row, add one to its revision, leave everything else alone.
delete from user_state where user_id = 'u_2';Remove that row.

The important word is where. It is the filter, and it is the difference between "update one row" and "update every row in the company". Leave it off an update or a delete and the database cheerfully does it to all of them, without asking. Chapter 1's intern, still employed.

One more word: an index. Without one, "find the row where id is u_2" means reading every row until it matches: fine at a thousand rows, awful at ten million. An index is a pre-sorted lookup kept beside the table so the database jumps straight there. Primary keys get one free.

Migrations: the schema has a history

You cannot edit a live database's shape by hand and hope, because other copies exist: local, production, maybe staging. So schema changes are written as files. A migration is one dated file of SQL moving the schema from the shape it had to the shape it should have, applied in filename order, once each, forward-only.

That is why "just add a column" is a migration. Every environment takes the change in the same order, or two databases that should be identical quietly stop being identical, and the bug that follows looks like code and is not.

Memento's database is Postgres, thirty years old and open source, rented running from Supabase with accounts and edge functions on top. Postgres also holds a database function: logic that lives and runs inside the database. That matters next.

Row Level Security: the clerk on the door

Here is the part everybody gets wrong. Every Supabase app ships with a public key so it can talk to the database at all. That key cannot be a secret, it sits in JavaScript on every phone. So "who may read this table" cannot be answered by the app. The app is the stranger.

Row Level Security is Postgres answering it instead. Switch it on for a table, then write a policy: a rule the database applies to every query by itself, deciding which rows this signed-in user may see or change. On with no policy, nobody gets anything. With the right policy, the exact same select * from user_state returns your row when you run it and their row when they run it. Not an error. Just fewer rows.

That is the trust boundary: the line past which you stop believing what you are told. Everything on the phone's side is a claim from a stranger. The database is the last place that can still say no.

ANY APP: rules in the database

Some rules are too important to live in the app, because the app runs on a stranger's device. "Never let a blank save wipe real work" is one. Written in the database, it is true for every client.

-- A stale or blank device may never overwrite meaningful cloud work.

ANY APP: the policy

Switch RLS on, then write the smallest rule that is true: "you may read the row whose owner column equals you." Reads and writes get separate rules.

MEMENTO: the read policy
create policy "Users can read own state"
  on public.user_state for select
  to authenticated
  using (auth.uid() = user_id);
supabase/migrations/20260724146000_least_privilege_boundaries.sql:12-15 (web pin ca8afc8)

Four lines. Reads only, signed-in callers only, your row only. The same migration drops the old insert and update policies, because sync_user_state is now the only write path, then revokes broad privileges from anon and authenticated rather than leaning on RLS as the only barrier.

ANY APP: one column or many tables

Model the data properly, one table per kind of thing, or put the whole app's state in one column as a blob. Both are real choices, trading the same thing in opposite directions.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

Firebase is Google's version: documents, not tables, with its own rules language. It works, it is not SQL, and your data is harder to take elsewhere. Your own Postgres gives total control, plus backups, upgrades, patching and a pager at three in the morning. A plain JSON file is what the practice sandbox uses: db.json, rewritten whole on every save. Fine for learning, useless the moment two people save at once. Supabase won because it is real Postgres, so the data stays portable and the queries ordinary, and because it puts the trust boundary where a client cannot argue with it. The cost is rent and a vendor whose defaults you check yourself. The one jsonb column won because state was already one JavaScript object, so phone and cloud hold the identical thing with nothing between them to drift. That bill is real: no counting users who finished Clarity without digging through JSON, and no indexing fields you never declared.

WHERE TODAY'S ANALOGY BREAKS

Breaks when: you picture the clerk serving one person at a time. A real database answers thousands of queries at once, two of which can hit the same row in the same millisecond. That is why sync_user_state contains for update, and why it carries a revision at all: two of your own devices can both save, and something has to pick a winner. Real model: a concurrent, transactional store where every statement either fully happens or fully does not, with a policy engine inside every query. "Who may see this row" has exactly one correct place to be answered, and it is not the phone.

RABBIT HOLE: what "security definer" means, and why it is a loaded gun

sync_user_state is declared security definer: it runs with its creator's permissions, usually an admin, not the caller's. That is how it writes to a table the caller may not touch directly, which is the design, since direct writes are dropped and this function is the only door. It is also how you build a hole, because anyone can call it. Two guards, both in the quoted lines: it raises 'Authentication required' when auth.uid() is empty, and it sets search_path to nothing, so an attacker cannot plant a same-named table the database would find first.
