Testing

A test is a sentence about your app, written in code, that the machine can check in a tenth of a second. Write enough of them and the question "did the agent break something" stops being a feeling and starts being a number.

LAST TIME

Errors come in three kinds: syntax, caught before anything runs; runtime, caught at the bad moment and printed with a stack trace; and logic, caught by nobody. A stack trace reads top down, and the useful line is the first one naming a file you wrote. The routine is reproduce, isolate, log the thing you assume.

Quick check

Which of the three kinds of error will your console never tell you about?
Logic. The program ran perfectly and produced the wrong answer, so nothing is red and nothing is thrown. Only a human, or a test, compares the answer to what it should have been. Chapter 23.
What is an exit code, and what does 0 mean?
The number a program leaves behind when it finishes. 0 means it worked, anything else means it did not. It is what a shell's && and every CI robot actually read. Chapter 6.
What is the difference between npm install and npm ci?
install resolves versions and can update the lockfile. ci wipes node_modules and installs exactly what the lockfile says, nothing newer. That is why CI uses ci: the same input every time. Chapter 19.

The idea

A test is code that runs your code and checks the answer. That is the entire concept. The checking part has a name: an assertion, a line that says "this must be true" and complains if it is not.

Every test, from a two line one to a monster, has the same three beats. Arrange, act, assert. Set up the situation, do the one thing, check the one answer. If you cannot see those three beats in a test, it is testing too much and you will not be able to tell what broke when it goes red.

// arrange: a person who completed yesterday, on a streak of 4
state = { streak: 4, lastCompleted: yesterday };

// act: they complete today
completeToday();

// assert: the streak went up by exactly one
expect(state.streak).toBe(5);
ANALOGY (TEMPORARY)

A smoke alarm you install yourself, one per room. Each one watches exactly one thing and screams when that thing is wrong. Adding rooms without adding alarms means the new rooms burn quietly. And a house full of alarms does not stop a fire; it tells you fast, while it is still small and in one room, which is the entire value.

The flip that makes it click

A failing test is not a problem. It is a specification, written in advance, in a language the machine can read. "The streak restarts at 1 after a gap" is an opinion when you say it in a meeting. Written as a test, it is a rule enforced on every push, forever, by a robot that does not get tired or take your word for it.

That is why writing the test first is not a purity thing. Write down what should be true, watch it go red, then make it go green. Red first matters because a test that has never failed has never been proven to check anything, and plenty of tests are quietly broken and pass anyway.

Three sizes

A unit test checks one function on its own: fast, precise, and a red one already names the file. An integration test checks pieces working together, this function plus the real storage, and catches the bugs that only exist in the seams. An end to end test drives the real app the way a person does: open it, tap it, look. Slowest, most honest, most likely to fail for reasons unrelated to your change.

A lot of the first, some of the second, few of the third. Not because the third is bad, but because a hundred of them take an hour and break on a Tuesday for no reason. Memento already has an end to end layer and it is a human one: the four cell screenshot law, where every visual change gets looked at at phone width and desktop width, dark and light, before it counts as done. The runner is Malik.

The runner

A test runner finds your tests, runs them all, and reports. Jest, the one Memento's native app uses, finds every file matching *.test.* or sitting in a __tests__ folder, runs each assertion, and prints a summary: how many passed, how many failed, and for each failure what it expected against what it got. Then it sets an exit code, and that number is the whole reason CI works. Zero is green, anything else stops the deploy.

Two warnings. Coverage is the percentage of your lines that ran while the tests ran. Easy to measure, which is why people chase it, and it says nothing about whether you checked the right thing: a test that calls every function and asserts nothing scores 100 percent. Coverage shows where you definitely have no tests. It never shows that you are safe.

A flaky test passes sometimes and fails sometimes with no code change, usually because of time, randomness, network or ordering. It is worse than no test, because a team that re-runs a red build has learned to ignore red. The fix is to stop depending on the real world: hand the function a clock instead of letting it read the wall clock, hand it a fake server instead of the real one.

The oracle

Here is the move that makes testing a rewrite possible. If you are rebuilding something that already works, you do not have to decide what the right answer is. The old code knows. Feed both the same input and assert they agree, and the old implementation becomes the oracle: the answer key. It is the highest leverage test you can write during a migration, and Memento has one.

ANY APP: the smallest useful test

Design values get changed by accident more than anything else in a codebase. Somebody adjusts a radius for one screen and moves it for forty. One test stating the agreed numbers turns that from a thing you notice in week three into a red line in nine seconds.

MEMENTO: tokens.test.ts, the whole file

import { tokens } from '../src/ui/tokens';

  expect(tokens.bootMark).toBe('#f5f5f7');
  expect(tokens.accent).toBe('#3ad9f5');
  expect(tokens.radius).toEqual({ small: 8, control: 10, card: 14, pill: 999 });
});

Arrange is the import, act is nothing because it checks a constant, assert is four lines.

ANY APP: pinning a rewrite to the original

When you rebuild working software the danger is not a crash. It is a quiet difference: the new version sends a slightly different request, or drops a field, and nobody notices for a month. If the old code still exists, make it the answer key and assert the new one matches.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The web app could have had a runner. Jest, or node's own built in one, would have found every tools/test-* file automatically and deleted that whole class of mistake. It does not, for the same reason it has no bundler and no build step: it was built to be edited and deployed in seconds, with zero tooling, by agents working in parallel. Every dependency added is a thing that can break a deploy at the worst moment. That bet bought speed, and the eighteen unrun scripts are part of the bill. The native rebuild took the opposite bet from day one: npm run check is typecheck plus the full suite, it runs in CI, and nothing merges red. Decide which one you would rather be holding the day an agent quietly changes a request body.

WORDS YOU NOW OWN
Test
Code that runs your code and checks the answer. A failing one is a spec for what should be true.
Assertion
The line that does the checking. "This must be true, and here is what to say if it is not."
Arrange, act, assert
The shape of every test: set up the situation, do one thing, check one answer.
Unit test
One function, alone. Fast, and red means you already know the file.
Integration test
Several pieces together. Catches the bugs that live in the seams between them.
End to end test
The real app, driven like a person would. Slowest, most honest. Memento's is the four cell screenshot law.
Test runner
The program that finds your test files, runs them, prints a summary, and sets an exit code. Jest, here.
Coverage
The share of lines that ran during the tests. Tells you where you have none. Never tells you that you are safe.
Flaky test
Passes sometimes, fails sometimes, no code change. Usually time, randomness, network, or order. Worse than no test.
Oracle
A known good implementation used as the answer key. During a rewrite, the old code is the best one you will ever have.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you start believing the alarms cover the house. A smoke alarm is passive: it watches whatever actually happens in that room. A test is not. It checks only the exact situation you thought to arrange, so a green suite proves one thing precisely: none of the cases you imagined are broken. The cases nobody imagined are invisible, and a full green run feels identical either way. Real model: tests are a ratchet. Each one locks in a behaviour you have already reasoned about so it cannot silently reverse, which is exactly the shape of risk you carry when two AI agents edit the same codebase. They stop regressions. They do not find the bug you have not met yet, and they say nothing about whether the thing was worth building.

RABBIT HOLE: mocks, and how a test lies to the code under test

Look again at the native tests and you will see jest.mock('react-native-mmkv', ...) and hand built ports objects with a fake http.post. Those are mocks: stand ins handed to the code so it never touches the real storage or the real network. Two reasons. Speed, because a real request is a thousand times slower than a fake one. And control, because you can make the fake fail with a 429 on demand and check what the app does, which is impossible to arrange with a real server. The catch is that a mock is your belief about how the real thing behaves, written down. When that belief is wrong, the test passes and the app breaks, and it is the most confusing failure in testing. It is also why the integration layer exists: something, somewhere, has to touch the real thing.
