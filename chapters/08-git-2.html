Git 2: branches, merges, conflicts, pull requests

Memento has 59 branches. Not 59 copies of the app: 59 sticky labels stuck onto snapshots in one chain. Once that lands, the Fable and Codex protocol you have run for months turns out to be a git diagram.

LAST TIME

A commit is a complete snapshot of the folder, not a list of changes, and each one points back at its parent to form a chain. Your work lives in three separate places: the working folder, the staging area, and the history in .git. A hash is a fingerprint of a snapshot, which is why you cannot rewrite the past without everyone seeing.

Quick check

Is a commit a record of what changed, or something else?
Something else: a snapshot of the entire folder. Git shows you changes by comparing a snapshot with its parent, but what is stored is the whole tree, deduplicated so unchanged files are stored once and pointed at many times.
You edit a file, run git diff, then git add it and run git diff again. Nothing prints. Did your change vanish?
No. git diff compares working folder to staging area, and after adding those two agree. git diff --staged compares staging to the last snapshot and shows it.
From chapter 2: Memento's sync sends p_expected_revision. What is that for?
Two devices overwriting each other. The device says which version it thinks is current so the database can refuse a stale write. Two agents in one git repo have the same problem, solved the same way.

The idea

A branch is a label that points at one commit. That is the entire definition: a small text file inside .git holding one hash. Making one copies nothing and takes about a millisecond however big the project is.

The label moves. When you are standing on a branch and make a commit, the new commit points back at the one the label was on, and the label slides forward onto the new one. So a branch marks the front end of one line of work, and the chain behind it is that line's history.

HEAD is a second label meaning "where you are right now". It points at a branch label, which is how git knows which one to slide forward when you commit. Switching branches moves HEAD and rewrites the files in your working folder to match that snapshot. The folder changes. Nothing is copied.

ANALOGY (TEMPORARY)

Bookmarks in one book, not two books. One history, one stack of pages, and you can have fifty bookmarks in it. Moving to another bookmark does not duplicate the book, it turns you to that page. You write a new page after the page your bookmark is on, then move the bookmark forward. Removing a bookmark does not tear out pages.

Merging, and the thing everyone panics about

Two lines of work exist and you want one. Merging is git working out what changed on each since they split and making a new commit with two parents. That commit is where the lines become one, and the graph records forever that they were separate.

Most of the time git does it without asking: if one line touched the Clarity screen and the other the sync code, nothing needs deciding. Git is not being clever. It compares line by line and notices no line was claimed twice.

A conflict is a line claimed twice: both lines changed the same lines of one file, differently. Git has no basis for choosing, so it stops, leaves the file with both versions marked out, and waits for a person. Nothing is broken, nothing is lost. A conflict is git refusing to guess. The markers are plain text in the file:

<<<<<<< HEAD
the north star is: ship the native app by November
=======
the north star is: ship the native app, Android too
>>>>>>> feature

Above the ======= is the branch you are standing on, below it the branch you are merging in. Delete the markers, leave the text you want, git add the file to say "resolved", and commit. You will do exactly that in a minute.

Rebase, in one paragraph

Rebase is the other way to combine work. Instead of tying two lines together with a merge commit, git lifts your commits off, moves you onto the tip of theirs, and replays yours on top. You get one straight line, and the history reads as if you had started from their latest work all along. The catch: replaying makes new snapshots with new hashes, so your old commit ids are gone and anyone who already had them is out of sync. Hence the rule, rebase your own unpushed work and merge everything else. Memento's standing instruction, at CLAUDE.md:72:

- **Before editing:** `git pull --rebase origin main` (get other agents' latest work).
CLAUDE.md:72 (native pin 93bfa796)

Read as a sentence: fetch whatever the other agent pushed, replay my commits on top, so history stays one clean line and collisions surface now instead of at push time.

The words for "somewhere else"

A remote is another copy of the repository, usually on a server. origin is the conventional name for the main one; Memento's is a private GitHub repo, malikpeace/memento. git push sends your commits there, git pull brings its commits down and combines them with yours. That is why --rebase is a pull option: it picks how to combine.

A pull request is not a git feature. It is a page on GitHub saying "here is my branch, every commit and every changed line in it, look before this goes into main". Comments attach to lines, a robot runs the tests, someone clicks merge. Its value is social: a second pair of eyes becomes required instead of encouraged.

Undoing: two words, very different consequences

Revert makes a new commit that undoes an earlier one. History grows, everything stays, and both the bad change and the undo are in the record. That is what "roll back the deploy" means, and it is safe even on work other people already have.

DESTRUCTIVE COMMAND. READ BEFORE YOU TYPE

Reset moves your branch label backwards. git reset --hard <hash> moves the label and overwrites your working folder to match, deleting every uncommitted change with no undo. On pushed work it also rewrites what others are building on. In git-lab, fine. In Memento, never. Reach for revert.

The safety net is reflog: a private local log of every position HEAD has been in, including ones no label points at. Move a label somewhere stupid and the commits are still there; git reflog finds their hashes. Local, never pushed, entries expire after about 30 to 90 days. A net with a time limit, not a resurrection machine.

See it

Branches and a merge, modelled. Watch that branches is only names pointing at ids, that branching adds no commits, and that the merge node is the one with two parents.

const commits = []; // the one and only history const branches = {}; // name -> commit id. Labels. That is all. let HEAD = "main"; // which label you are standing on function commit(message, parents) { const id = "c" + (commits.length + 1); commits.push({ id, message, parents: parents || [branches[HEAD]] }); branches[HEAD] = id; // the label slides forward return id; } branches.main = null; commit("start"); commit("work on main"); branches.feature = branches.main; // a new branch: zero commits copied console.log("after branching, commits:", commits.length, "| labels:", JSON.stringify(branches)); HEAD = "feature"; commit("work on the branch"); HEAD = "main"; commit("different work on main"); HEAD = "main"; commit("merge feature into main", [branches.main, branches.feature]); console.log("labels now:", JSON.stringify(branches)); commits.forEach(c => console.log(c.id, "parents:", (c.parents || []).join(",") || "none", "|", c.message));

Deleting the feature line from branches would remove the label while every commit stays in the array. That is why deleting a branch is not dangerous: you throw away a sticky note, not pages.

Now that a hash is a fingerprint of a snapshot, read approved @ b6e148b2 properly. It does not mean "the Doors work is approved". It means this exact snapshot of the entire folder, fingerprint b6e148b2, was reviewed and found good. One snapshot, not the branch. And it cannot be fudged: change one character of one file and the next commit has a different fingerprint, so the old approval visibly does not cover it. That is why the subjects also say what is owed, like "(Codex re-review owed)". Every commit after an approval is unpinned until somebody reviews again and writes a new hash down. THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The normal alternative is GitHub pull requests: branch, open a PR, get line comments and an approval attached to a commit automatically, merge through a button that can be blocked until the tests pass. It is better at all of that, and Memento will need it the moment a second human touches the code. It was skipped because the reviewers are two AI agents that cannot click a button and communicate only through files in the repo. Writing "approved @ hash" into the log is the cheapest thing carrying the same guarantee. The cost: nothing enforces it, so the gate is you.

WORDS YOU NOW OWN
Branch
A movable label pointing at one commit, stored as a one-line text file. Making one copies nothing; deleting one throws away the label, not the commits.
HEAD
The label meaning "where you are standing". Switching branches moves it and rewrites your working folder to match.
Merge
Joining two lines of history with a commit that has two parents. Usually automatic.
Conflict
Both lines changed the same lines of one file, so git stops and writes both versions in with markers. A request for a decision, not a breakage.
Rebase
Replaying your commits on top of someone else's latest work: one straight line, new hashes. Fine for your own unpushed work.
Remote and origin
A remote is another copy of the repo. origin is the conventional name for the main one. push sends, pull fetches and combines.
Pull request
A GitHub page for reviewing a branch before it joins main: line comments, test results, an approval attached to one commit.
Revert
A new commit that undoes an old one. History grows, nothing is lost, safe on shared work. What "roll back the deploy" means.
Reset
Moving your branch label backwards. --hard also overwrites your working folder and destroys uncommitted work. Banned in Memento.
Reflog
A local log of every position HEAD has been in, including ones no label points at. Your way back after a bad move, for a few weeks.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you assume the pages are safe forever because you only threw away a bookmark. Git keeps a commit alive as long as something can reach it: a branch label, a tag, or a reflog entry. Delete the last label pointing at a line of work and those commits become unreachable, sit in the reflog for roughly 30 to 90 days, then get swept away by garbage collection. Also, a book has one order of pages and a git history is a graph: a merge commit has two parents, so "the page before this one" can have two answers. Real model: a directed graph of immutable snapshots, a few mutable one-line pointers into it, and a reachability rule deciding what is kept. Every git command either adds a node or moves a pointer.

RABBIT HOLE: why merge conflicts are a people problem

Git's conflict detection is dumb on purpose: it compares text line by line and has no idea what the code means. So it catches same-line edits and misses the dangerous kind, where one agent renames a function and the other adds a call to the old name in a different file, both merge cleanly, and the app breaks at runtime. That is a semantic conflict. No version control system catches it; only tests and review do. It is the deeper reason the plan insists on one owner at a time for state, auth and the router.
