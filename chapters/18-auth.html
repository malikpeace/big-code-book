Auth: who you are and what you may do

Two questions that look like one. Who is this? And is this person allowed to do that? Mixing them up is how a paywall becomes decorative, and Memento's own decision log says its web paywall currently is.

LAST TIME

A database is tables of rows, related by keys, described by a schema that migrations change one dated file at a time. Row Level Security is Postgres deciding, inside every query, which rows the signed-in user may touch. Three of chapter 4's four incidents are that rule being absent.

Quick check

What does using (auth.uid() = user_id) actually do?
It is the rule Postgres applies to every query on that table. auth.uid() is the database asking who is calling. If that does not equal the row's user_id, the row is not in your results. Not an error. Just absent.
Why can the Supabase public key sit in JavaScript on every phone without that being a disaster?
It identifies the app, not a person, and access is not decided from it. RLS decides from who is signed in. With RLS off, the same key is a skeleton key, which is what happened to 170 Lovable apps.
A request comes back with 401. What did the server mean?
"I do not know who you are, and this route needs to know." Different from 403, which means "I know who you are and you still may not." That difference is this whole chapter.

The idea

Authentication is who are you. You prove it once: a code to your email, a password, a face. The answer is an identity, nothing more.

Authorization is what may you do. Given that identity, may you read this row, call this route, use the paid model. Yes or no, per action.

Knowing who someone is tells you nothing about what they may do. Every hotel understands this: the desk checks your ID once, and the key card opens your room and the gym and not the wine cellar.

ANALOGY (TEMPORARY)

The hotel. You show your passport at the desk once: authentication. They hand you a key card: the session, proof you were checked, valid for your stay. The number on the card is the token. You present it at every door, and the door has no idea what your passport looked like. Cards expire, can be reissued, and can be cancelled while you stand in the lift. The valet gets a different key entirely, one that starts the car and will not open the boot. That valet key is OAuth.

The token, properly

A token is a string, sent in a header with every request, usually as Authorization: Bearer <the string>. Four things about it are the model.

PropertyWhy it exists
It is issued by the auth system, not made up by the clientIt is signed, so the server tells a real one from a guess with no lookup.
It expires, usually in an hourSo a stolen one stops working soon. Memento's native session stores expiresAt per session.
It can be refreshedA second, longer-lived refresh token quietly trades itself for a new access token, so you are not signed out every hour.
It can be revokedSigning out, or an admin killing the session, stops it working before it expires.

So a token is not a password. It is a temporary, cancellable stand-in, which is why apps hand them around instead of storing passwords anywhere.

OAuth, and the key you do not give away

"Continue with Google" is not Memento asking for your Google password. Memento sends you to Google, Google authenticates you on its own page, and Google returns a signed statement saying "this is a real account, here is its id and email". Memento never sees the password, so it could not leak it if it tried. And you can revoke the connection later, which you could not do after typing a password into somebody's form.

Public keys, secret keys, and one flag that means nothing

Some keys identify an application. Some authorize spending money. Treating them alike is how founders get four-figure bills.

Supabase's anon key is the first kind: a long string inside every copy of the app, visible to anyone who opens the developer tools. It says "requests from the Memento app", not who you are. It is still a real credential the API accepts, so it is not powerless. It is publishable because its power was deliberately cut down: the database role it maps to gets almost no grants, and RLS decides access per row from the signed-in identity. Public by design, safe only because of the previous chapter.

The Anthropic key is a secret key, the second kind: anyone holding it can spend Memento's money. It lives in the edge function's environment and nowhere else, which is the entire reason the chapter 16 proxy exists.

Then the flag. An entitlement is what an account has paid for, and a real one lives on a server. Memento's entitlements.isPaid is a boolean on the user's own device, editable in ten seconds. Fine as a hint about which screen to draw, never evidence. A client can say it is paid. Only a server can know.

And the bug: the client sends its own isPaid and the server believes it. Run it, then read the fix.

// THE BUG: the server trusts a flag that came from the client. function badServer(request) { if (request.isPaid) return "expensive AI answer (billed to the founder)"; return "paywall"; } // A normal user's app sends this: console.log("honest client:", badServer({ user: "u_2", isPaid: false })); // Anyone who opens the dev tools sends this: console.log("edited client:", badServer({ user: "u_2", isPaid: true })); // THE FIX: the server ignores the claim and asks the system that knows. const entitlements = { u_2: false, u_9: true }; // server-side truth function goodServer(request, whoTheTokenSays) { if (!whoTheTokenSays) return "401, who are you"; if (!entitlements[whoTheTokenSays]) return "402, payment required"; return "expensive AI answer"; } console.log("edited client, good server:", goodServer({ isPaid: true }, "u_2")); console.log("real paid user:", goodServer({ isPaid: false }, "u_9")); console.log("no token at all:", goodServer({ isPaid: true }, null));

The fix is not better validation of isPaid. The field is gone from the decision: the server uses the identity the token proved, and its own records.

ANY APP: do not trust your own sign-in reply

ANY APP: tokens do not live with the data

Saved app data gets copied, backed up, exported and logged. A token in there is a token in all of those places. Use the operating system's locked store instead.

MEMENTO NATIVE: the keychain, this device only

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative is passwords you store yourself: hashing, reset emails, breach notifications, permanent liability, zero product value. Memento does not have one. Web sign-in is a six-digit code to your email plus Google; native is the same code path. The cost is real, since a code email in a spam folder is a failed sign-in and your support ticket. What Memento buys is that it never holds a password, so it can never leak one. The honest gap. The web paywall is not enforced anywhere, and Memento's own decision log says so: "The paywall is UI-only today: Unlock sets state.entitlements.isPaid = true on the client (js/13), no payment collected, so the paid gate is currently bypassable. Real billing enforcement is the #1 pre-launch gap." That is DECISIONS.md:18-21 (web pin ca8afc8): the third sandbox's bug, in production, written down by the people who built it. The native side is where it gets fixed, which is why paidServerAuthority was born as a literal false.

WORDS YOU NOW OWN
Authentication
Who are you. Proved once, producing an identity.
Authorization
What may you do. Asked again at every door, per action.
Session
The record that you were checked, valid for a while. The hotel key card.
Token
The string you send with each request that stands for the session. Signed, expiring, refreshable, revocable. Never a password.
Refresh token
A longer-lived second token whose only job is to get you a fresh access token without signing in again.
OAuth
Another service vouching for you. Google authenticates you on its own page and hands back a signed statement. Memento never sees the password.
Anon key / public key
A publishable credential that identifies the app and carries a deliberately limited database role. Safe to publish because grants and Row Level Security keep its authority small, not because it has none.
Secret key
Spends money or grants power. Lives in a server's environment and nowhere else. Memento's Anthropic key is one.
Entitlement
What a given account has paid for. Real ones live on a server. isPaid on a phone is a drawing hint, not evidence.
Secure store / keychain
The operating system's locked box for credentials. Tokens go there, not in the app's saved data.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you picture the door phoning the front desk. Most tokens are signed, so the door verifies the signature itself with no call, which is also why revoking is not instant: a signed token stays valid until it expires unless something extra checks a revocation list. The hotel also has one guest per card, where real sessions live on several devices at once, and signing out on one does not sign out the others. Real model: a signed, short-lived, scoped claim about an identity, issued by a party both sides trust, verified independently at each boundary, with a refresh path and a way to revoke. You will not build one. You will decide, over and over, whether a check is asking the client or asking the server.

RABBIT HOLE: what is actually inside a token

Most of these are JWTs, JSON Web Tokens: three chunks separated by dots. The first two are plain JSON, encoded but not encrypted, holding the algorithm and the claims, which include the subject (your user id), an issuer, an audience, and exp, the expiry. Anyone can read them. The third is a signature over the first two, made with a key only the issuer has. So the contents are not hidden; holding it is what proves you were given it. That is why the database can call auth.uid() with no lookup, and why the native app keeps tokens in the keychain. To see one, sign in on the web and look at the sb- entry in localStorage.
