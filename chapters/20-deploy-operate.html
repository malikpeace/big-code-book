Deploy and operate

Code on your Mac helps nobody. This chapter is the last hop of the journey: how a change becomes something on a stranger's phone, what stands between the two, and what the job turns into once it is live.

LAST TIME

A dependency is borrowed code with a version number, package.json is what you asked for and the lockfile is what you got. Humans run npm install, robots run npm ci. A secret is a value the code needs and must never contain, so it arrives from the environment at run time, and a leaked key gets revoked, not deleted.

Quick check

Why do robots run npm ci instead of npm install?
Because ci reproduces the lockfile exactly and fails if the lockfile and package.json disagree. install may resolve a range to something newer, so the robot could test a different app than the one you wrote.
Chapter 17: what is a migration, and why are they forward-only?
A dated, numbered change to the database's shape, kept as a file. Forward-only because the database already holds real rows, so you add a new step rather than editing one that already ran.
Chapter 15: what is a status code for?
It is the one-line verdict on a request. 200 worked, 4xx means you asked wrong, 5xx means the server broke. It is how a caller decides what to do next without reading the body.

The idea

There is more than one copy of your app, and the copies are not equal. An environment is one running copy, with its own data, its own settings, and its own audience. Three are normal.

EnvironmentWho sees itWhat breaking it costs
localYou, on your MacNothing. Break it constantly.
staging or devYou and your testersAn hour. Fake data only.
productionReal users, real moneyTrust, and sometimes data you cannot get back.

The separation is the whole point. Production has real people's notes in it, so if the only copy is production, every experiment is an experiment on your customers. The day an agent decides to tidy the database is the day you find out you had no other copy. That is the Replit incident from chapter 4.

Now the two verbs people mix up. A build turns source into the thing that actually runs: it bundles files, strips comments, shrinks names, and produces an output folder. Running happens afterwards. Not every app needs a build. Memento's web app has none, because a browser reads its files directly. The native app needs one, because a phone cannot read a folder of TypeScript.

Between "I finished" and "users have it" sits a robot. Continuous integration, CI, is a machine that wakes up on every push, checks out your code on a clean rented computer, and runs your checks. No opinions, no bad days. If a check exits non-zero, it refuses, which is chapter 6's exit code doing the most important job it will ever do.

If the checks pass, the robot can deploy: copy this exact version to the place users reach. That place is hosting, a computer somewhere that answers when someone knocks. The knocking works because of DNS, the internet's phone book, which turns a name like mementoapp.co into the number of a machine. You rent the name, point it at your host, and the phone book spreads the answer around the world over the next few hours.

ANALOGY (TEMPORARY)

A newspaper. Your laptop is the reporter's notebook: scribble anything, nobody cares. Staging is the proof copy, printed once, read by two people looking for typos. Production is the print run on the truck. The robot is the sub-editor who will not let a page through with a hole in it. Deploying is the truck leaving. And DNS is the phone book that tells a stranger which address the paper comes from. Once the truck is gone, you cannot un-print. You can only print a correction and send another truck.

Cache busting, and why it is the bug you will hit

Browsers and phones keep copies of files so pages load fast. That is a feature until you ship a fix and the user keeps getting yesterday's file, because as far as the browser knows, app.js is app.js. The fix is to change the address: app.js?v=1378 is a different URL, so nothing cached can answer it. That is cache busting. A bundler does it for you with a hash of the file's contents in the filename. By hand it works exactly as well, right up until a human forgets.

When it goes wrong

Every version you ship is a commit, so undoing a bad deploy is undoing a commit. Rollback is git revert of the offending commit and a push, and the robot deploys the corrected version the same way it deployed the broken one. Note what you do not do: edit production by hand, or force-push history away. A revert is a new commit saying "undo that", which keeps the record, and the record is how you stop it happening twice.

Then there is the day something is wrong and you do not know what. Three moves, in this order, and the order is the lesson.

  1. Stop the bleeding. Roll back, or flip the feature off. Do not debug a live fire.
  2. Tell the users. Before they tell you. A short honest line beats silence every time.
  3. Then find the cause. Calmly, with the logs, once nobody is being hurt by it.

Step three needs somewhere to look. A log is the app writing down what it did, and every layer keeps its own: the browser console for the phone, the backend dashboard for the server, the CI run log for the deploy. Knowing which of the three to open is most of the skill.

Two more operator facts. A backup is a scheduled copy of the data, and restoring one puts the database back to a moment in time, throwing away everything after it. A backup you have never restored is a hope. And cost: some vendors bill per month, some per call, and the per-call ones are the ones that surprise you, because a loop with a bug spends money at machine speed.

See it

A CI pipeline, whole, in fifteen lines. Checks in order, stop at the first failure, hand back an exit code. Everything after this is the same idea with more YAML.

const CHECKS = [ { name: "syntax", run: () => true }, { name: "typecheck", run: () => true }, { name: "tests", run: () => false }, // flip this to true and run it again { name: "deploy", run: () => true } ]; let code = 0; for (const check of CHECKS) { if (check.run()) { console.log(" pass " + check.name); continue; } console.log(" FAIL " + check.name); code = 1; break; // nothing after a failure runs } console.log(code === 0 ? "deployed." : "exit code " + code + ", live is unchanged.");

Notice the break. Deploy is the last item in the list, so a red test is a closed door, not a warning. Flip the tests to true, run it again, and watch it open.

Same file, different address

const cache = new Map(); function load(url) { if (cache.has(url)) { console.log("from cache: " + url); return; } cache.set(url, "fresh bytes"); console.log("downloaded: " + url); } load("js/01-state.js?v=v1377"); load("js/01-state.js?v=v1377"); // the phone already has this one load("js/01-state.js?v=v1378"); // one character changed. it is a new URL. load("js/01-state.js"); // and no tag at all is a fourth address console.log("addresses the phone thinks exist: " + cache.size);

Three downloads from three addresses, for one file. The browser is matching strings, nothing more. That is the entire mechanism behind every "it works on my machine but his phone shows the old version" conversation you will ever have.

Now in Memento

ANY APP

A deploy pipeline answers four questions, and you can read any project's by looking for them.

When does it run? A trigger: which branch, which files.

What must pass? The gate: the checks, and whether it stops at the first red.

Where does it copy to? The target, and with what permission.

How do I undo it? Revert and push, or nothing, which is not an answer.

MEMENTO

The gate, first half. Every JavaScript file is parsed before anything moves:

          for f in memento-app/js/*.js; do
            node --check "$f" || { echo "SYNTAX ERROR in $f"; fail=1; }
          done
          if [ "$fail" != "0" ]; then
            echo "::error::A JS file failed the syntax check. Deploy aborted; live is unchanged."
            exit 1
          fi

/* v980: the JS build stamp. The release sed bump rewrites the version in BOTH

   ONCE on mismatch. Kills the "phone silently runs old cached js under a new

window.MEMENTO_JS_BUILD = 'v1378';

The shell declares a version, the scripts declare a version, the boot code compares them. Mismatch means the phone is running a stale mix, so it repairs itself once. Three times in one day is why that code exists: an operations problem solved inside the app.

Last, the kill switch. Real billing does not turn on because code shipped, it turns on because an environment variable says so:

Read the default. Anything unset, misspelled or unrecognised lands on disabled. Turning real payments on is one setting in a dashboard, and turning them off in an incident is the same setting, with no deploy and no waiting. That is what an operations control looks like.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The obvious alternative is one repo, made public, served straight from Pages. Simpler, and wrong here: the repo holds migrations, workflow files, internal handoff documents and the whole agent protocol, none of which is anyone's business. So the private repo stays private and a robot mirrors only memento-app/ into a public one, which also means the public repo can never hold a file the app does not serve. The second alternative is a real host with a build step, giving automatic cache busting and proper environments, at the cost of a build, an install, and a pipeline that can break on its own. Memento bought the no-build simplicity and pays for it in hand-written ?v= tags and a hand-listed test block, with the boot-time build stamp as the net for the one failure mode that trade creates.

WORDS YOU NOW OWN
Environment
One running copy of the app with its own data and settings. Local, staging, production. Keeping them apart is what stops an experiment becoming an incident.
Build
Turning source into the thing that runs. Memento's web app skips it entirely; the native app does it with expo export.
CI
A robot that checks out every push on a clean machine and runs your checks. A non-zero exit code means it refuses.
Deploy
Copying one exact version to where users reach it. In Memento it is an rsync from a private repo into a public one, triggered by a push.
Hosting
The computer that answers when someone knocks. Memento's web app is served by GitHub Pages out of the mirrored repo.
DNS
The phone book from a name to a machine. It is why mementoapp.co and a github.io address can be the same app.
Cache busting
Changing the address so a cached copy cannot answer. A bundler does it with a content hash; Memento does it by hand with ?v=v1378.
Rollback
Revert the commit, push, let the robot deploy the corrected version. Never edit production by hand.
Log
The app writing down what it did. Browser console for the phone, Supabase dashboard for the edge functions, the Actions run log for the deploy.
Backup and restore
A scheduled copy of the data, and putting the database back to a moment in time, which discards everything after it. Untested backups do not count.
Kill switch
A setting that turns a dangerous capability off without a deploy. POLAR_PRODUCTION_MODE defaults to disabled, so unset means off.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you think the truck delivers everything at once. A web deploy lands on the server instantly, but each phone picks it up only when that phone next asks, which is why caches and service workers can leave one user on last week's version while everyone else has today's. There is no single moment when everyone is on the new version, and pretending otherwise is how you ship a change that assumes old and new clients cannot coexist. The newspaper also has no database: a printed correction cannot un-write data, but a bad migration can, and no rollback of the code brings back a column you dropped. Real model: a deploy makes a new version available at an address. Clients converge on it at their own pace. Code can be reverted because it is versioned. Data cannot, which is why backups, not rollbacks, are the safety net that matters, and why the database and the code have to be able to survive each other being one step out of date.

RABBIT HOLE: why a DNS change "takes time"

Nobody asks the authoritative server every time. Answers are cached, all the way down the chain: your phone, your router, your internet provider, and the resolvers in between. Every answer comes with a TTL, a time to live, which says how long it may be reused. So when you point a name at a new machine, the old answer keeps being handed out until the TTLs expire, and different people switch over at different times. That is the whole reason for the advice to lower the TTL a day before a move: you are asking the world to stop holding the old answer for so long. It is the same mechanism as the ?v= tags, one layer down, and it fails the same way.
