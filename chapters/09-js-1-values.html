JavaScript 1: values, variables, types

Every line of Memento moves values around and hangs names on them. Get the names right and the rest of the language is small. Get them wrong and you will misread code for years.

The idea

There are two separate things, and almost every beginner welds them into one.

A value is a piece of data. The number 7. The text "stellar". The answer true. Values exist whether or not anyone has named them. They live in memory, in those numbered slots from chapter 1.

A variable is a name you hang on a value so you can talk about it later. Chapter 1 called it a name tag, not a box, and that phrasing is the whole chapter, so here it is with the consequences attached.

ANALOGY (TEMPORARY)

Baggage claim. The suitcases are the values. They sit on the carousel whether or not anyone has claimed them. A variable is a luggage tag with a name written on it, tied to one suitcase. streak = 10 means "tie the tag that says streak onto the suitcase holding 10". Re-assigning means untying the tag and tying it to a different suitcase. The tag was never a container. Nothing was ever inside the name.

Three things follow from the picture, and each kills a misconception that survives in most people for years.

A name points at exactly one value at a time. Never two. People say "the variable holds the old value and the new value" because the box picture lets them imagine a box with two things in it. There is no box. Move the tag and the old suitcase is simply no longer tagged by that name.

The equals sign is not an equation. streak = streak + 1 would be nonsense in maths. In code, = is an instruction: work out the right side, then point the left name at the result. Read it as "becomes", never as "equals". This single re-reading fixes more confusion than anything else in the chapter.

Tying a second tag copies nothing. let best = streak reads the value streak points at right now and points best at that. From then on the two names are independent. There is a real exception for objects and arrays, it causes genuine bugs, and it is chapter 11's job.

Types: what kind of thing the value is

Every value has a type, which is simply what kind of thing it is. The machine uses the type to decide which rule to apply. Six of them cover almost everything you will read in Memento.

TypeLooks likeMeans
string'stellar', "Malik", ''Text. Quotes make it text. Single or double, pick one.
number7, 0, 1.5A number. No quotes. Whole and decimal are one type here.
booleantrue, falseA yes or no. Only two values exist.
nullnullDeliberately empty. A human wrote "there is nothing here on purpose".
undefinedundefinedNever given a value. Nobody decided anything. The machine's shrug.
array[], ['health', 'work']An ordered list. Square brackets.
object{ name: 'Malik', streak: 4 }A bundle of named values. Curly braces. The workhorse of the language.

The most expensive type bug in the world is a number that arrived as text. Chapter 1 showed you "7" + 5 gluing into "75". It happens because a raw form input and a raw localStorage value both come back as a string, every time. Parsing fixes it: JSON.parse hands you real numbers and booleans again. Skip the parse, and a quiet piece of text wanders into your maths. typeof asks a value what it is, and it is the cheapest debugging tool in the language.

let, const, and what const actually protects

You create a name with let or const. let means this name may be pointed elsewhere later. const means it may never be moved once tied. Memento uses const by default, so when you read a diff, a let is a small signal that something changes.

Here is the part people get wrong. const freezes the tag, not the suitcase. const state = { streak: 4 } then state.streak = 5 is completely legal, because the tag never moved. Only state = somethingElse is refused. Hold the sentence: const locks the name, not the thing.

Quotes, backticks, and equals signs

Text in quotes is literal. Text in backticks is a template literal, which lets you drop a value into the middle with ${...}. Memento's AI prompts and most of its screen copy are built this way. Comparing values uses strict equality, three equals signs: === asks "same type and same value". There is also a two-equals version, ==, which converts types before comparing and says "7" == 7 is true. It exists, you will see it in old code, and you should never write it. Three, always.

Last thing: a comment starts with // and the machine ignores the rest of the line. Comments are humans talking to humans across time. Chapter 1's shim file was twenty lines of exactly that.

Now in Memento

ANY APP

Every app decides what it remembers about a user and writes that shape down somewhere, usually as one object with named keys: a starting template, empty on day one, filled in as the person uses the product. Reading that template is the fastest way to understand any codebase, because it is the list of everything the app believes exists.

Each starting value's type is a promise. '' promises text. 0 promises a number. [] promises a list. null is a slot a human deliberately left empty.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative is many small variables: userName, isPaid, clarityTheme, a few hundred of them scattered across 38 files. That reads fine in any one spot and is a disaster everywhere else, because saving would mean listing every name by hand and forgetting one means silent data loss. With one object, saving is JSON.stringify(state), syncing is one parcel, resetting is pointing the name at a fresh copy of DEFAULT_STATE, and adding a feature is adding a key. The cost is that every part of the app can reach into one shared thing, so a careless change anywhere can corrupt anything. Chapter 14 shows the write path, chapter 17 shows the database refusing a blank overwrite.

WHERE TODAY'S ANALOGY BREAKS

Breaks when: two tags end up on the same suitcase. With plain values that never matters, because you can never edit the number 7. With objects and arrays you can edit the value itself, so two names pointing at one object means a change through either name is visible through both. At baggage claim that would be two tags on one suitcase, and someone repacking it while you watch a different tag. Real model: a variable holds a reference to an object, and assignment copies the reference, not the object. That is chapter 11, and it is where half of all "but I did not change that" bugs come from. The tag picture stays correct the whole way through. What changes is what you are allowed to do to the suitcase.

RABBIT HOLE: why typeof null says "object"

Run console.log(typeof null) and it prints "object", which is wrong and everybody knows it is wrong. It is a bug from the first version of JavaScript in 1995, when types were stored as a small tag on each value and the tag for null happened to be all zeroes, the same as the tag for objects. It has never been fixed because fixing it would break an unknown number of pages on the live web. Keep it as a souvenir: production software carries its history forever, and "we cannot fix it because people depend on the broken behaviour" is a sentence you will meet again in your own product.
