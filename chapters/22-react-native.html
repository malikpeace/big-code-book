The idea

A component is a function that takes inputs and returns a description of what should be on screen. Not a class, not a widget, not a magic object. A function.

Its inputs come from two places. Props are handed down by whoever used the component, and it may not change them: the parent's data, on loan. State is the component's own memory, and when it changes the component runs again and the screen updates. Same props and same state, same screen, every time.

ANALOGY (TEMPORARY)

A chef at a station. The ingredients come from the kitchen, already chosen, and the chef cannot change what was sent. That is props. In the chef's pocket is a notebook with tonight's plate count. That is state. Given the same ingredients and the same notebook, the chef plates the identical dish every time. When the notebook changes, the dish is plated again and the new plate replaces the old one.

Redrawing, and why nobody touches the screen

Chapter 14 gave you the two styles. Memento's web app is imperative: something happens, code finds the element, code edits it. React is the other one. You never edit the screen. You change state, React calls your component again, compares what it returns with what is on screen, and applies the smallest set of real changes itself. That second run is a re-render, cheap because it is mostly comparison. The payoff: the screen cannot drift out of step with the data, because it is only ever produced from the data. The cost: you say what you want, not how to get there, which feels backwards for about a week.

What the function returns

Components return JSX, HTML-shaped syntax inside JavaScript: <Text>{label}</Text>. It is not HTML and not a string. The build turns every tag into a function call, so that line becomes roughly createElement(Text, null, label). Curly braces drop a value into the middle, and a capitalised tag is one of your own components. Nesting them builds the component tree: a screen is a component holding components, down to the ones that actually draw something. Reading an unfamiliar React app means finding the top of that tree and walking down.

Hooks: how a function remembers

A function forgets everything when it returns, so React provides hooks: functions whose names start with use, which attach memory to a component.

HookGives youUse it when
useStateA value and a setter: const [n, setN] = useState(0)The screen must change when this changes.
useEffectWork that runs after drawing, plus a function that undoes itTimers, subscriptions, anything outside React.
useRefA box that survives redraws and never causes oneYou must remember something the screen does not show.
useCallbackThe same function object across redrawsHanding a function to a child that would otherwise redraw for nothing.

The one that bites people is useEffect. It takes a job and a list of things to watch, and it may return a cleanup function. React runs that cleanup before running the job again, and when the component leaves the screen. Start a timer with no cleanup and it fires into a screen that no longer exists. Half the crashes in a young React app are exactly that.

React Native: same model, no browser

React Native keeps all of the above and changes the tags. There is no DOM. <View>, <Text> and <Pressable> become the real native views iOS and Android already have, so scrolling, text selection and the keyboard are the platform's own. Styling is a style object in JavaScript instead of a CSS file: same properties, camelCased, no cascade, no selectors, in the component's own file.

Expo is the toolkit around it: build system, native modules, packaging. expo-router turns files into screens, so src/app/index.tsx is the first screen and src/app/_layout.tsx wraps everything. Running on a phone needs a dev build: a real app installed once, holding the project's native pieces, that loads your JavaScript over the network as you edit. On a Mac it runs in the simulator, a fake iPhone in a window that belongs to Xcode, which is why Xcode is installed even though nobody opens it. Shipping means Apple's review and a cut of anything bought inside the app.

React will not run in this page, so here is a model of it: thirty lines that behave like React and are not React. Components are functions returning strings of HTML, and one render rebuilds the root from state. Press Run, then tap the button.

Each is a function of props, returning what to draw. function StreakText(props) { return '<p>' + props.days + ' day streak</p>'; } function HoldButton(props) { return '<button id="hold">' + props.label + '</button>'; } // The tree: one component made of the other two. function App(s) { return StreakText({ days: s.streak }) + HoldButton({ label: s.done ? That is the whole idea. } function render() { document.getElementById('root').innerHTML = App(state); document.getElementById('hold').onclick = function () { setState({ streak: state.streak + 1, done: true }); }; console.log('re-rendered, streak is now ' + state.streak); } render(); </script>

Nothing there reaches into the page to edit a number. The click changes state, the screen is rebuilt from state. Real React does the same, except it compares old and new trees and touches only what differs. Delete the render() call inside setState and you get the web app's classic bug: the data moves and the screen does not.

A real component, top to bottom

export function HoldToComplete(props: {
  theme: Theme; typeface: Typeface; width: number;
  onComplete: () => void;
  completed?: boolean;      // actionDoneToday(): the control is inert while true
  actionKey?: string;       // a new key re-arms a finished control
  label?: string; icon?: React.ReactNode;
}) {
  const { theme, typeface, width } = props;
  const labelFont = typeface(700);
  const label = props.label ?? 'Hold to complete';
  const progress = useSharedValue(0);
  const holding = useRef(false);
  const finished = useRef(false);
  const timer = useRef<ReturnType<typeof setTimeout> | null>(null);
  const onComplete = useRef(props.onComplete);
  onComplete.current = props.onComplete;

  const clearTimer = () => { if (timer.current) { clearTimeout(timer.current); timer.current = null; } };

  // A new action identity re-arms the control (js/08 rebinds per render).
  useEffect(() => {
    finished.current = false; holding.current = false; clearTimer();
    cancelAnimation(progress); progress.value = 0;
  }, [props.actionKey, progress]);
  // Unmount: nothing may fire afterwards.
  useEffect(() => () => { clearTimer(); holding.current = false; }, []);

The props list is the component's contract, typed by chapter 21. onComplete: () => void is how a child talks back up: the button does not know what completing means, only who to tell.

Then four useRef calls, and why they are refs and not state is the lesson. Whether a finger is down changes many times a second and must never redraw the button. A ref survives every redraw and never triggers one. State is for what the screen shows, refs for what the component must remember.

Two effects, both about cleanup. The first watches props.actionKey: a new action arrives, cancel the animation, re-arm. The second's body is a function, so it does nothing going in and runs that function on the way out. When the button leaves the screen, kill the timer, because a timer firing into a component that no longer exists is a crash.

  const begin = useCallback(() => {

THE NATIVE VERSION (declarative)

There is no equivalent function, and that is the point. State changes, the components that read it run again, and every part is correct because it was drawn from the new state. Nobody keeps a list of what to refresh. The trade: less control over exactly when a piece of screen updates, in exchange for a guarantee that it cannot be forgotten.

// Memento Jr, React Native version. READ ONLY, there is no v3 sandbox yet.
import { useCallback, useEffect, useRef, useState } from 'react';
import { Pressable, StyleSheet, Text, View } from 'react-native';

const HOLD_MS = 3000;

export function HoldToComplete(props: { done: boolean; onComplete: () => void }) {
  const [holding, setHolding] = useState(false);   // the screen shows this
  const timer = useRef<ReturnType<typeof setTimeout> | null>(null);

  // Leaving the screen must not leave a timer behind.
  useEffect(() => () => { if (timer.current) clearTimeout(timer.current); }, []);

  const begin = useCallback(() => {
    if (props.done) return;                        // guard clause, chapter 10
    setHolding(true);
    timer.current = setTimeout(() => {
      setHolding(false);
      props.onComplete();                          // tell the parent, do not decide
    }, HOLD_MS);
  }, [props.done, props.onComplete]);

  const cancel = useCallback(() => {
    if (timer.current) clearTimeout(timer.current);
    timer.current = null;
    setHolding(false);
  }, []);

  return (
    <Pressable onPressIn={begin} onPressOut={cancel} disabled={props.done} style={styles.button}>
      <View style={styles.row}>
        <Text style={styles.label}>
          {props.done ? 'Done for today' : holding ? 'Keep holding' : 'Hold to complete'}
        </Text>
      </View>
    </Pressable>
  );
}

const styles = StyleSheet.create({
  button: { minHeight: 44, borderRadius: 8, paddingVertical: 12, paddingHorizontal: 16, backgroundColor: '#ffffff' },
  row: { flexDirection: 'row', alignItems: 'center', justifyContent: 'center', gap: 8 },
  label: { fontSize: 15, color: '#0b1112' },
});

Two props, one piece of state, one ref, one cleanup, two callbacks, three tags. The real one adds a typed theme, an animation, haptics, a re-arming key and an inverted twin layer sweeping across the label. Same skeleton.

The four answers

Props: theme, typeface, width, onComplete required; completed, actionKey, label, icon optional. All typed in the signature at line 22.

State: almost none, which is the interesting answer. Nothing uses useState. There is a shared animation value and four refs: holding, finished, timer, and one holding the latest onComplete. None of them redraw, because none of them are what the screen shows.

Cleanups: the first effect re-arms on a new actionKey: clear the timer, cancel the animation, reset progress. The second returns a function and does nothing else, so its whole job is the unmount cleanup: clear the timer, drop the holding flag, so nothing fires after the button is gone.

At three seconds: the setTimeout from begin fires finish, which refuses if the finger lifted or it already fired, marks itself finished, triggers a light haptic whose failure is swallowed on purpose, and calls onComplete.current(). The parent decides what completing means.

WORDS YOU NOW OWN
Component
A function that takes props and returns what to draw. The unit everything else is made of.
Props
Inputs handed down from the parent. Read only. Data goes down the tree, never up.
State (in a component)
Memory the component owns. Changing it redraws. Only for things the screen shows.
Re-render
React calling your function again after state changed, comparing the result to what is on screen, and applying the difference.
JSX
HTML-shaped syntax that the build turns into plain function calls. Capitalised tag means your component.
Component tree
Components nested inside components. Where you start reading an unfamiliar app.
Hook
A use-prefixed function that gives a component memory or behaviour. Called in the same order every render, never inside an if.
useState / useRef
A value plus a setter, changing it redraws / a box that survives redraws and never causes one.
useEffect and its cleanup
Work after drawing, plus the function that undoes it. The cleanup runs before the next run and when the component leaves.
useCallback
Keeps the same function object between renders so children do not redraw for nothing.
Reducer
A pure function from (state, event) to the next state. Where a big flow's logic lives, testable without a screen.
Style object
Styles as JavaScript next to the component. Same properties as CSS, camelCased, no cascade.
Expo / expo-router
The toolkit around React Native / the router where a file in src/app/ is a screen.
Dev build
A real app installed once, holding the project's native pieces, that loads your JavaScript as you edit.
Simulator
A fake iPhone in a window on the Mac, provided by Xcode. Not a real device, and it will lie to you about safe areas and performance.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you believe the dish really is plated from scratch. React produces a fresh description, then changes only the parts of the real screen that differ. Native views that stayed are the same objects they were, which is why a text field keeps its cursor through a re-render and the chef picture predicts the opposite. It breaks again on refs, effects and timers, the chef reaching outside the station: they survive re-plating, and uncleaned they carry on after the chef has gone home. Real model: a component is a description of a screen, re-run when its inputs change, and anything outside that description is created and destroyed by hand through effects.

RABBIT HOLE: why hooks may not go inside an if

React does not know your hooks' names. It matches them by call order: first, second, third. A hook inside an if changes the count between renders, so React hands your second hook the memory belonging to your third. Hence the rule, hooks at the top level always, enforced by a lint rule in every React project alive. One strange rule, in exchange for components that stay simple functions instead of classes.
