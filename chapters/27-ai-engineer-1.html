The AI-assisted engineer, part 1: asking, plans, diffs, claims

Twenty-six chapters were the prerequisites. This is the job. Four moves, in order, every time: ask properly, approve the plan, read the diff, verify the claim. Miss one and you are guessing about your own product.

LAST TIME

Software gets structured to keep related things together and unrelated things apart, so a change has a small blast radius. Memento's two architectures make opposite bets: 38 numbered global scripts with no import graph, and typed folders with one. Debt is a loan you took to move fast, and the interest is charged on every future change.

Quick check

An agent pushed a commit that broke the home page. revert or reset?
Revert. It makes a new commit that undoes the bad one, so history grows and nothing is lost, and it is safe on work other people already pulled. Reset moves your branch label backwards and, with --hard, destroys uncommitted work.
A change comes back with 90% test coverage. Is it correct?
No. Coverage measures which lines a test ran through, not whether anything useful was asserted about them. A test that calls a function and checks nothing gives full coverage and zero information.
Why can Memento's Supabase anon key sit in the client while the Anthropic key cannot?
The anon key only identifies the project; what it may read is decided by row rules inside the database. The Anthropic key is a bearer credential: whoever holds it can spend your money, so it lives in the edge function's environment and never reaches a browser.

The idea

You cannot read every line an agent writes. Nobody can, which is the point of using one. So the job is putting checkpoints where a mistake is still cheap, and refusing to move past one that has not been passed.

Four of them, in a deliberate order. A wrong sentence in a request costs nothing. A wrong plan costs a minute. Wrong code costs a review. Wrong code that shipped costs a customer. Every checkpoint you skip pushes the mistake into a more expensive one.

ANALOGY (TEMPORARY)

Hiring a contractor for a kitchen. You do not stand behind him holding each tile. You agree what the room should look like, you read the quote before work starts, you walk the room before you pay, and you turn the taps on yourself. Four moments. The rest of the week he works and you do not.

1. The five-part ask

An agent guesses. Chapter 1 said it: the machine obeys, the agent interprets. Every gap you leave gets filled with a guess, and the guesses are plausible, which is worse than wrong. A five-part ask closes the five gaps that cause damage.

PartWhat it stops
What. One change, stated in one sentence.Two changes in one diff, which you can no longer review or revert separately.
Where. Named files.The agent hunting, finding a second place that looks similar, and editing both.
Symptom or goal. What you saw, or what you want to be true.Fixing the thing you described instead of the thing that is wrong.
Done-condition. How a machine could tell."Done" meaning "I stopped typing".
What not to touch. The files that are off limits.Scope creep, which is chapter 28's whole first half.

The done-condition is the one people skip and the one that matters most. Anthropic's guidance for Claude Code puts it plainly: give the agent something it can check itself, and if you cannot verify it, do not ship it (code.claude.com/docs/en/best-practices). A done-condition is that check, written before the work starts, by the person who will be angry if it is wrong.

The same request twice. Consistency is Memento's streak module.

THE BAD ASK
the streak is broken, fix it

Five gaps: which streak, broken how, which file, what would prove it fixed, what is off limits. The agent answers all five confidently, and you find out which answers it picked by reading a diff you did not expect.

THE GOOD ASK
WHAT: the current streak counts a day twice when the phone
crosses midnight in a different timezone.

WHERE: memento-app/js/06-consistency-mori.js only.

SYMPTOM: test account flew Toronto to London on 14 Sep.
Home showed a 7 day streak, then 8, with one day logged.

DONE WHEN: _currentStreakFrom returns 7 for that day list,

DO NOT TOUCH: js/01-state-foundation.js, css/base.css, or

The good ask is longer because each line removes one guess, not because longer is better. Note the last sentence. You will write it every time.

2. Review the plan before you allow code

A plan is the agent's statement of intent before it acts. Anthropic's recommended shape is explore, plan, implement, commit, and OpenAI's Codex guidance is the same shape in different words (developers.openai.com/codex/learn/best-practices). Reading a plan takes a minute. Reading the code it produced takes twenty.

Six questions. Any "no" sends it back.

  1. Does it name the files? A plan with no file names has not read your codebase yet. It is describing software in general.
  2. Does it say what it will not touch? If it does not, the boundary exists only in your head.
  3. Does it mention existing code it will reuse? A plan that names no existing function is about to write a second one. This is the duplicate-system tell, a chapter early.
  4. Does it say how it will verify? Not "I will test it". Which command, which screen, which output.
  5. Is it smaller than the ask, or bigger? Bigger means scope creep already started. Smaller sometimes means it found a simpler route, which is good, and sometimes means it misunderstood, which is not. Ask which.
  6. What is the rollback? One commit you can revert is a rollback. Eleven files across two systems is not.

Score a plan against those six in code, so the questions stop being vibes:

const plan = { files: ["js/06-consistency-mori.js"], wontTouch: ["js/01-state-foundation.js", "css/base.css"], reuses: "_currentStreakFrom, already in that file", verifyBy: "", // nothing here. that is the finding. stepsAsked: 1, stepsPlanned: 3, rollback: "revert the single commit" }; const questions = [ ["names files", plan.files.length > 0], ["says what is off limits", plan.wontTouch.length > 0], ["reuses existing code", plan.reuses !== ""], ["says how it verifies", plan.verifyBy !== ""], ["not bigger than the ask", plan.stepsPlanned <= plan.stepsAsked], ["has a rollback", plan.rollback !== ""] ]; let passed = 0; questions.forEach(q => { console.log((q[1] ? "ok " : "SEND BACK ") + q[0]); if (q[1]) passed++; }); console.log("score:", passed, "of 6. Any miss is a send-back, not a warning.");

Two failures, and they are the expensive two: no verification step, and three steps for a one-step ask.

3. Inspect what actually changed

The agent's summary is a summary. The diff is the record. They disagree more often than you would like, and only one of them shipped.

MoveWhat it answers
git diff --statWhich files, how many lines each. The ten-second scan. More files than your ask named is the scope-creep alarm.
git diffEvery changed line, with surrounding context.
git diff --stagedWhat is about to go into the commit, which is not always the same thing.
The diff pane in your editor or desktop appThe same information, side by side, easier on a big screen. Same data, nicer window.
Asking "what files did you touch, exactly"A list you can then check against --stat. When the two disagree, you have learned something important about that session.

Read every hunk. Not every file, every hunk. A hunk is small by definition, and the dangerous edits are always small.

Line by line. The @@ says old line 210, six lines; new line 210, twenty-two. The three lines with a leading space are context, the function signature and the promise, unchanged, there to orient you. Then sixteen + lines and no - lines, which means nothing was deleted and the old behaviour still sits underneath.

5. Ask why, not what

Anthropic ran a controlled trial in February 2026: 52 mostly-junior developers learning an unfamiliar library. The AI-assisted group scored about 17 points lower on a comprehension quiz. But the participants who used it for conceptual questions, why this pattern, what does this do, scored 65% or better, level with the people who wrote everything by hand (anthropic.com/research/AI-assistance-coding-skills, summarised in research/research-pedagogy.md section 1.9). Delegation cost comprehension. Inquiry did not. Same tool, opposite result, decided by the grammar of your sentence.

Do-question (costs comprehension)Why-question (keeps it)
Fix the streakWhy does the streak walk backwards from today instead of forwards from the start?
Add caching hereWhat would break if this ran twice in the same second?
Clean up this fileWhich two jobs is this function doing, and which one does not belong?

Two phrases carry the weight. "Explain, then stop" removes the assumption that an explanation is a preamble to editing. "What would break if" is the fastest way to find out whether it understands the code or is describing what the code looks like it does. Every chapter of this book ends with one of these, and that is not decoration.

6. Verify a claim

"It works" is a feeling the agent is reporting about itself. Verification is something a machine produced that you can look at: pasted output, a test result with assertion names, a screenshot of the actual screen, an exit code. No artifact, nothing verified, however confident the paragraph.

7. The seven tells of a hallucination

A hallucination is not a lie and not a glitch. It is the most plausible continuation, and a filename that fits your naming convention is extremely plausible. Which is why each one dies to a single line.

The tellThe one-line check
A file path that sounds rightls memento-app/js/31-streak-utils.js
A function it says it changedgrep -n "getStreakDays" memento-app/js/*.js
"Tests pass" with no output"Paste the exact output, including the summary line."
A library API that does not existgrep -rn "dayjs" memento-app/ and check package.json for the native side
A confident date, number, or version"Where did that number come from? Name the file or the URL."
A claim about behaviour with no line number"Which file and line proves that?"
"I verified it" with no artifact"Show me the artifact. Screenshot, output, or exit code."

Six of those are one command. The seventh is one sentence. That is the entire defence, and it is why this is a founder-sized skill rather than an engineer-sized one.

ANY APP

None of the four checkpoints survive on willpower. An agent starts every session with no memory, so rules living in your head reach it only when you retype them. The fix the industry converged on in 2026 is a harness: a rules file read at the start of every session, a map of where things live, and wherever possible a machine that checks the rule instead of a model asked to remember it.

The harness is also what makes reviewing cheap. If the rules file says where a feature lives, "the diff touched a file outside that list" becomes a yes or no question, which is a question you can ask at midnight on a phone.

MEMENTO

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative is a short harness, which several practitioners recommend, because a long rules file competes for the model's attention with the actual task and rules nobody enforces become decoration. Memento went the other way: a long, specific, incident-shaped file where most rules name the exact bug that caused them (v854, v692, v811, the purple box, the OLED band). The bet is that a rule with its own origin story attached gets followed, and the receipts support it, since the repeat failures stopped. The cost is real. The file map at the top has drifted from the files it describes, and chapter 28 opens with what drift like that produces. A harness is a thing you maintain, not a thing you write.

WHERE TODAY'S ANALOGY BREAKS

Breaks when: you treat the contractor as slow and expensive, so you batch work up and check in weekly. An agent is fast and cheap, which inverts the economics: many small asks with a checkpoint after each beat one big one inspected at the end. A contractor also remembers last Tuesday. An agent starts every session with nothing, so anything you have not written into a file, you have not said. Real model: a tireless, literal collaborator with amnesia, no stake in the outcome, and a strong bias toward reporting success. The four checkpoints are the only place your judgment still enters the system.

RABBIT HOLE: why the plan is easier to review than the code

A plan is written in your language, so reviewing it uses what you already know: what the feature is for, which files exist, what is off limits. Code review needs all that plus the language. That gap is why plan review is the highest-leverage habit here for a non-engineer, and why practitioners keep converging on explore, plan, implement, commit. The trap: a plan is also the easiest thing to produce convincingly. One naming no files and no existing functions was written without reading your codebase, and it will read beautifully. The six questions separate a plan from an essay about a plan.
