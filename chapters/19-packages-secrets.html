Packages, dependencies, secrets

Most of the code that ships in your app was written by strangers, and you agreed to it by typing one command. This chapter is about what you agreed to, how to see it, and the one class of value that must never be written down in the code at all.

LAST TIME

Authentication is who you are, authorization is what you may do, and they are different questions answered by different code. A token is a ticket with an expiry, not a password. Memento's anon key is public on purpose because Row Level Security, not secrecy, is what protects the rows.

Quick check

Why does Memento's phone call an edge function instead of calling Anthropic directly?
Because calling Anthropic needs a key, and anything the phone holds, a user can read. The proxy also owns the model, the prompt and the spend ceiling, so an anonymous caller cannot dress up expensive work as free work.
You delete a line from a file and commit. Is the old line gone?
No. The commit that contained it is still in the history. Git is a chain of snapshots, so deleting forward never erases backward. Remember this, it is half of today's chapter.
Chapter 6: what is the number a command leaves behind, and who reads it?
The exit code. Zero means it worked. && reads it to decide whether to run the next command, and so does every deploy robot, which is chapter 20.

The idea

A package is a folder of somebody else's code with a name and a version number, published to a shared library on the internet. When your project uses one, that package is a dependency: your app does not run without it. A date formatter, a gesture handler, a way to draw a blurred panel, all of it already exists, free, one line away.

The line is in a file called package.json, which sits at the top of a project and is its identity card: the name, the version, the commands, and the list of borrowed code. Then you run npm install, and npm goes to the registry, the public warehouse at registry.npmjs.org, and downloads everything on the list into a folder called node_modules.

Your list is not the real list. Every package you asked for has its own package.json, with its own dependencies, which have theirs. Those are transitive dependencies, and they arrive without anyone asking. Ask for one router and twelve hundred folders land on your disk. You did not choose them, you did not read them, and they are now running inside your product.

ANALOGY (TEMPORARY)

You hire a plumber and write on the job sheet "a plumber, version 3-ish". The plumber shows up, and he brings his own electrician, who brings his own apprentice. At the end you get a receipt that names the exact humans who walked in, which van, which day. The job sheet is what you wanted. The receipt is what you got. Rehiring from the job sheet next month gets you a different crew. Rehiring from the receipt gets you the same crew.

Semver, and what the little symbols mean

Version numbers are not decoration. Almost every package follows semantic versioning, three numbers separated by dots, and each one is a promise:

PartExamplePromise
major1.4.2Something broke on purpose. Your code may need changing.
minor1.4.2Something was added. Your code still works.
patch1.4.2Something was fixed. Nothing else changed.

Now the symbols. ^1.4.2 means "this or newer, up to but not including 2.0.0", so patches and features arrive on their own. ~1.4.2 is tighter: patches only. And 1.4.2 with no symbol means exactly that one, until a human changes the line. That last one is pinning, and it costs you free bug fixes in exchange for this: nothing about your app changes while you sleep.

Ranges are why the lockfile exists. package-lock.json is written by npm, not by you, and it records what actually got installed: every package, the resolved version, the URL, and an integrity hash of the bytes. It goes in git. It is the reason the app on your Mac and the app on the robot's machine are the same app.

Two commands that look alike and are not. npm install reads package.json, works out what satisfies the ranges, and updates the lockfile if it found something newer. npm ci ignores all that and reproduces the lockfile exactly, failing loudly if the two disagree. Humans install. Robots ci.

One more rule, and it is the one founders skip. An upgrade is a change. Bumping a dependency is not housekeeping, it is shipping thousands of lines of code you did not read. It gets a branch, a test run and a review, exactly like a feature.

See it

Fifteen lines that answer the question you will actually have when you read a package.json: does this range accept that version? Predict the twelve answers before you press Run.

function parse(v) { return v.split(".").map(Number); } function accepts(range, version) { const [rMaj, rMin, rPat] = parse(range.replace(/^[\^~]/, "")); const [maj, min, pat] = parse(version); if (maj !== rMaj) return false; // a new major is NEVER automatic if (range[0] === "^") return min > rMin || (min === rMin && pat >= rPat); if (range[0] === "~") return min === rMin && pat >= rPat; return min === rMin && pat === rPat; // no symbol: exactly this one } for (const range of ["^1.4.2", "~1.4.2", "1.4.2"]) { for (const v of ["1.4.2", "1.4.9", "1.5.0", "2.0.0"]) { console.log(range + " accepts " + v + " ? " + accepts(range, v)); } }

The caret lets 1.5.0 in. The tilde does not. Nothing lets 2.0.0 in, because a major bump is the author saying out loud that he broke something. One wrinkle the real npm has and this toy does not: below 1.0.0 the rules tighten, so ^0.2.3 behaves like a tilde and stops before 0.3.0.

The tree, and why node_modules is enormous

Ask for one thing, get five. That is the whole lesson, and it scales badly in your favour and in nobody else's.

const REGISTRY = { "expo-router": ["query-string", "expo-linking"], "query-string": ["decode-uri-component"], "expo-linking": ["expo-constants"], "decode-uri-component": [], "expo-constants": [] }; const downloaded = new Set(); function install(name, depth) { const isNew = !downloaded.has(name); console.log(" ".repeat(depth) + name + (isNew ? "" : " (already have it)")); if (!isNew) return; downloaded.add(name); for (const child of REGISTRY[name]) install(child, depth + 1); } install("expo-router", 0); console.log("you asked for 1 package. you downloaded " + downloaded.size + ".");

Five names here. In the real native app the same walk ends in the thousands, and node_modules is the biggest folder on the project by a distance. It is never committed, because it is derived: the lockfile plus one command rebuilds it, so storing it would be storing the answer next to the question.

The half of this nobody teaches until it is too late

Installing a package runs a stranger's code on your machine. Not later, at install time: npm packages can declare install scripts that execute the moment they land. That is the whole attack surface, and it has three well-known shapes. A maintainer's account gets taken over and a poisoned version is published under a name millions of projects already trust. A package is named one letter away from a popular one, which is typosquatting, and it waits for a fumbled command. Or a tiny, boring, unpaid package deep in your tree changes hands, and the new owner is not who you think. Collectively that is supply chain risk, and it is why npm install <something-i-just-googled> is never free.

The defences are unglamorous and they work: pin versions, commit the lockfile, let robots run npm ci, read what an upgrade changed, and prefer fewer dependencies. Every package you do not add is a package that cannot betray you.

Secrets: the value the code must never contain

A secret is a value your code needs at the moment it runs and must never be embedded in client code, committed to history, logged, or shown to anyone who should not have it: an API key, a database password, a billing token. It can be written down in a protected place, a local .env that git ignores or a secret manager the host reads at runtime. Write one into a normal source file and it gets saved, committed, pushed and published, and it is in the history forever.

So the value is handed in from outside when the program starts, as an environment variable. You met those in chapter 6 as echo $HOME. Same mechanism, serious job. On a server you set them in the hosting dashboard. On your Mac you keep them in a .env file, a list of NAME=value lines, and the first thing you do is add it to .gitignore.

There is one convention worth knowing because it trips people up. In an Expo app, any variable named EXPO_PUBLIC_SOMETHING is baked into the app the user downloads. That is public by prefix: the name itself is a promise that the value is not secret. Nothing secret ever gets that prefix, and a name without the prefix never reaches the phone.

And the part that hurts: if a key does leak, deleting the line does nothing. The old commit still has it. You revoke the key at the vendor, which makes the leaked string worthless, and you issue a new one. Deleting is theatre. Revoking is the fix.

Three of those four lines are real Memento code, and they all pass. The fourth is the shape of a mistake. Scanners like this run on every push at real companies, and they are smoke alarms, not fireproofing.

ANY APP

Four things you can check on any project in about two minutes, and they tell you how seriously it takes this.

Is there a lockfile, and is it committed? No lockfile means every install is a dice roll.

Are versions pinned or open? Carets everywhere means the app changes itself.

Does .gitignore block .env and key files? If not, a leak is scheduled, not possible.

Do secrets appear only as names? Search the repo for the word KEY. You should find lookups, never values.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The web app could have used a framework and a build step. It would have got an import graph, module boundaries and automatic cache busting, paid for with a few hundred packages, an install step before anyone can see a change, and a permanent upgrade treadmill. Memento took the opposite deal: three dozen plain JavaScript files loaded in order by number, no install, no build, and a whole class of risk that does not apply. The native app cannot make that trade, because React Native is packages, so it takes the other defence: pin nearly every version, commit an 11,554-line lockfile, and vendor a patched copy of one broken transitive dependency. Two apps, two strategies, one rule underneath: know exactly what is in the building.

WORDS YOU NOW OWN
Package / dependency
A named, versioned folder of someone else's code that your app needs to run. Published to the npm registry, listed in package.json.
package.json
A project's identity card: name, version, commands, and the list of borrowed code with the version ranges it accepts.
Lockfile
package-lock.json. Machine-written, committed to git. The exact version, URL and content hash of every package that actually landed, including the ones you never asked for.
Semver
major.minor.patch. ^ accepts new minors, ~ accepts patches only, a bare number accepts nothing new. A major bump is the author saying he broke something.
Transitive dependency
A package your packages brought with them. You did not choose it and it runs in your app anyway.
node_modules
The borrowed code on disk. Derived from the lockfile, enormous, never committed.
npm install vs npm ci
Install resolves ranges and may update the lockfile. ci reproduces the lockfile exactly and fails if it disagrees with package.json. Humans install, robots ci.
Supply chain risk
A package can run code when it installs, a maintainer's account can be stolen, and a name can be one letter off. Every dependency added is trust extended to a stranger.
Vendoring
Copying a dependency into your own repo so you control its contents. Memento does it for one patched package, under a private version number.
Secret
A value the code needs and must never contain. It arrives from the environment at run time and lives in the hosting dashboard, not in a file.
.env and .gitignore
A local file of NAME=value lines, and the list that tells git to pretend it does not exist. Commit the example, never the real one.
Public by prefix
EXPO_PUBLIC_* is baked into the downloaded app on purpose. The prefix is a promise that the value is not secret.
Revoke
What you do to a leaked key. Deleting the line does nothing, because the old commit still has it. Revoking makes the string worthless.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you picture subcontractors as people who leave at the end of the day. A dependency never leaves. Its code sits inside your running app, on the same side of every trust boundary you have, with the same access to the same data. A plumber also cannot be replaced overnight by a stranger who bought his van and kept the name painted on the side, which is exactly the supply-chain attack. The receipt leaks too: the lockfile does not only record what arrived, it can cause what arrives, because npm ci reads the lockfile first and the ranges second. Real model: package.json is a set of constraints, the lockfile is one solved solution to those constraints plus a content hash per package, and node_modules is that solution unpacked onto disk. A secret is never part of any of it: it is a value the operating system hands the process at start, which is why it can be rotated without touching a line of code.

RABBIT HOLE: why does a tiny package have a thousand folders under it

The npm ecosystem grew a culture of very small packages, each doing one thing, each depending on a few others. It made publishing easy and it made trees deep. The famous demonstration was left-pad in 2016: one developer unpublished an eleven-line package over a naming dispute and broke builds across the industry for hours, because thousands of projects depended on it without knowing. npm changed its unpublish rules afterwards. The structural lesson survived: the danger in a dependency tree is almost never the package you chose, it is the fourth-level one you have never heard of, maintained by one unpaid person, that everything quietly rests on.
