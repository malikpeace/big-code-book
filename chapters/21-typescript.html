TypeScript: types as contracts

Memento's rebuild is written in a language that refuses to build until the shapes line up. That refusal is the cheapest bug-catcher you own, and it works while you sleep.

LAST TIME

Code goes from your machine to a build, from a build to a host, and a robot reviewer runs on every push so a broken commit never reaches a phone. Production is one environment among several, and rolling back means shipping a commit that undoes the last one. Logs, alerts and backups are where you look when it goes wrong at 2am.

Quick check

In plain JavaScript, what does "7" + 1 give you, and why?
"71". The machine saw text on the left and applied the glue rule instead of the arithmetic rule. Nobody was warned, nothing crashed. That silence is what this chapter attacks.
Chapter 20: what does CI actually do when you push?
A computer checks out your commit, runs the checks the project listed, and reports pass or fail. Same commands you could run yourself, run every time so nobody can forget. Memento's native workflow runs a type check, the tests, and an export build.
Chapter 19: why is EXPO_PUBLIC_FEEL_SAMPLE safe in a repo and ANTHROPIC_API_KEY is not?
The EXPO_PUBLIC_ prefix means the value gets baked into the app that ships to phones, so it is public by design and only ever holds switches. The API key is a password that spends Malik's money, so it lives in Supabase's secret store and the phone never sees it.

The idea

A type annotation is a note next to a name saying what shape of value may go there. streak: number means this slot takes numbers. Everything else in this chapter is that one idea stacked.

Chapter 9 gave you the types themselves. They exist in plain JavaScript too, but only while the program runs, and nobody checks them in advance. You find out dailyTime became "30" when a customer sees NaN.

TypeScript is JavaScript with a second program attached that reads your code and checks every one of those notes against every place the value is used. That program never runs your app. It reads it, the way a proofreader reads a manuscript.

ANALOGY (TEMPORARY)

A proofreader who never reads for sense. Before the book prints, one person checks only the mechanics: every footnote points at a source that exists, every cross-reference names a real chapter, every name spelled the same way each time. They cannot tell you the argument is wrong. They can tell you page 212 points at a chapter that was cut. It catches a class of mistake careful reading never catches, because it is boring and mechanical and a human gets tired.

The parts you will actually read

Annotations go after a colon. const name: string = 'Malik'. Functions annotate their inputs and their answer: function dayKey(date: Date): string reads as hand me a Date, I hand you back a string. That line is a function signature, usually all you need to use a function you have never seen.

Shapes get names. A type alias is type State = { streak: number }. An interface does nearly the same job with different words, and the difference matters to library authors, not to you. Read both as a named shape.

A question mark makes a field an optional property: system?: string may be absent, and the proofreader forces you to cope with that. A vertical bar makes a union type: string | null is one of those two, and 'off' | 'deep' is one of exactly those two words. Unions are the most useful thing in the language, because most real answers in software are one of a small set of possibilities and plain JavaScript cannot say that out loud.

You do not annotate everything. Type inference works out the obvious ones: write let streak = 0 and the proofreader knows that slot is a number and rejects streak = "0" later. Good TypeScript is mostly inferred, with annotations at the edges where a shape enters or leaves.

Strict mode turns on the paranoid checks. The best one: a value that might be null cannot be used until you have dealt with the null. That single rule deletes the most common crash in every JavaScript app ever written.

Then the part everybody gets wrong on first contact. Types are erased before the code runs. The build strips every annotation and the phone executes plain JavaScript, exactly as if you had never written a type. Types are not a runtime safety net and cannot check what a server sends you.

So the check is a command you run on purpose. npm run typecheck runs tsc --noEmit: read every file, report every violation, produce no output. The proofreader with the printing press switched off. Typechecking is what CI runs on every push, and a failing typecheck is a build that does not ship.

Why this matters more now than it did in 2015

An agent writing code makes a specific kind of mistake: something that reads beautifully and refers to a property that does not exist. state.lastDone when the field is lastCompleted. In plain JavaScript that line runs, evaluates to undefined, and the screen quietly says "never" forever. In TypeScript it does not compile, and the agent is told so in seconds, usually before you see the diff. Types are one of very few tools that catch an AI's mistakes with no human looking. Tests are the other, and tests cost a person's time. The annotation was going to be written anyway.

Now in Memento

ANY APP

Anything that talks to a network needs two shapes written down: what a request looks like going out, and what an answer looks like coming back. Answers come in two flavours, worked and did not work, so the reply is a union of a success and a failure.

Writing those shapes at the top of the file is a habit worth stealing. Shortest documentation there is, it cannot go stale, and every call site gets checked against it free.

Read Message slowly. role is not a string, it is one of two exact strings, so role: 'system' is an error at the keyboard. Message[] is a list of those, so nothing but a well formed message enters the pipe. The question marks carry the rest: messages is required, everything else is optional. One thing mandatory, the rest knobs.

Now the function that builds a Result, and the line that turns HTTP numbers into words.

export function extract(data: any): Result {
  const text=Array.isArray(data?.content)?data.content.find((b:any)=>b?.type==='text' && typeof b.text==='string')?.text:undefined;
  if (data?.stop_reason==='refusal') return {status:'failure',code:'refusal'};
  if (data?.stop_reason==='max_tokens') return {status:'failure',code:'truncated'};
  if (typeof text!=='string' || !text.trim()) return {status:'failure',code:'empty'};
  return {status:'success',text:text.replace(/[\u2014\u2013]/g,' - '),stopReason:String(data.stop_reason||''),model:String(data.model||'')};
}

Four exits, every one a member of the union. The signature (data: any): Result is a promise the proofreader enforces: add a fifth exit returning { ok: true } and the file stops compiling. Note data: any going in. any means stop checking this one, honest here because that value came off the network and nobody can know its shape in advance. Every ?. and typeof in the body earns back by hand what the types could not give. Types describe your code, not the outside world.

A type that proves something

memento-native/src/billing/accessPolicy.ts:42-43 (native pin 93bfa796)

That return annotation is not boolean. value is AccessReceipt is a type predicate: it returns true or false, and when it returns true the proofreader treats that value as a real receipt from then on. A runtime fact promoted into a compile-time one. The input is unknown, the strict cousin of any: you may hold it, you may not touch a property until you prove what it is. Right for data out of storage, which chapter 18 taught you never to trust.

The <T> is a generic: a blank in the contract the caller fills in. Whatever you are storing, call it T, hand me a function that proves a value is a T, and everything I give back is about T. One storage module serves every screen and none of them lose their types.

Types for code that has none

Memento's pure rules were ported from the frozen web app as plain JavaScript, on purpose, so the logic stays comparable with the original. To let typed code call them, a human wrote the shapes by hand next to each file: a declaration file, .d.ts, signatures with no bodies.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative is sitting in the same repo, and you have been reading it for twenty chapters. memento-app/ is plain JavaScript: no types, no compiler, no build step, roughly 67,000 lines. The payoff was real. Edit a file, reload the browser, done, and deploys that are a file copy.

The bill was real too. Two AI agents wrote most of those lines, and not one misspelled property, wrong argument count or forgotten null was ever caught before a human looked at a screen. Nothing in that codebase can tell you mechanically that a caller and its function disagree. Every check is a person. So the rebuild flipped it: TypeScript strict from the first commit, tsc --noEmit in CI, and hand-written .d.ts files for the logic that could not be retyped. The cost is a build step and annotations to maintain. The purchase is a proofreader that reviews every agent's work in seconds, forever, for free.

WORDS YOU NOW OWN
TypeScript
JavaScript with a proofreader attached. You write down shapes, the proofreader checks every use of them, and none of it exists once the code runs.
Type annotation
The note after a colon that says what may go in a slot. streak: number.
Function signature
What a function takes and what it gives back, written as one line. Usually all you need to use it.
Type alias / interface
A name given to a shape so you can reuse it. Read both as "here is a named shape".
Optional property
A field marked with ?. It may be missing, and strict mode makes you handle that.
Union type
A | B. One of these, never something else. How software says "success or failure" out loud.
Type inference
The proofreader working out the obvious types itself, so you only annotate the edges.
Strict mode
The paranoid setting. Its best rule: a maybe-null value cannot be used until the null is dealt with.
Type erasure
Types are stripped before the code runs. The phone executes plain JavaScript. Types are never runtime protection.
Typecheck
tsc --noEmit. Read everything, report every violation, produce no files. Run by CI on every push.
any / unknown
"Stop checking this" / "I do not know yet, and you may not touch it until you prove what it is". Prefer the second.
Type predicate
A return type written value is Thing. A runtime check that promotes its result into a compile-time fact.
Generic
A blank in a contract that the caller fills in, written <T>. One module serving many shapes without losing any of them.
Declaration file
A .d.ts file: signatures with no bodies, hand-written so typed code can safely call untyped JavaScript.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: data arrives from outside. A proofreader checks every cross-reference inside the manuscript and has no opinion about a letter arriving in the post tomorrow. Write const reply: Result = await response.json() and TypeScript believes you completely, because the annotation is a claim you made, not a fact it verified. Real model: types stop existing at runtime. Anything crossing a boundary, the network, storage, a form field, must be validated by code that really runs, which is why extract() is full of typeof checks and validateReceipt takes unknown. Chapter 25 calls this the trust boundary.

RABBIT HOLE: the type check is not a proof

A passing typecheck means the shapes agree, not that the code is correct. function streakFor(user: User): number { return 0; } typechecks perfectly and is completely wrong. Logic is still on you, and on chapter 24's tests. Anyone who says a typed codebase does not need tests is selling something.
