JavaScript 4: async, promises, the event loop

Memento waits about two seconds for the AI and the screen never freezes. That is not speed. It is one cook who refuses to stand and watch the oven, and once you can see the timer board on the wall, out-of-order log lines stop being spooky.

Control flow is where the finger goes next: down, skip, or back. A loop is separate passes in order, never all at once. Two names can hold the same object because a name holds an address, which is why const backup = state backs up nothing and try / catch is a net under a block that might explode.

The idea

Chapter 10's pile of index cards had a hole in it. If a program is one finger walking one line at a time, and a line says "ask a server in another country for an answer", the finger stands there for two seconds. No scrolling, no typing, no animation, no redraw. The app looks dead.

That is exactly what would happen, and it is why the language has the machinery this chapter is about.

One thread, a queue, and a waiting list

JavaScript runs your code on one main thread. One finger. There is no second finger running your functions beside the first, ever.

Next to it sit two more things. A queue: a line of jobs waiting their turn on the thread, first in, first out. And a waiting list: work handed off to something that is not JavaScript and is not ready yet. A timer counting down. A network request in flight. Your thread does not run those. The browser does, in the background.

The event loop is one rule, repeated forever: when the thread is empty, take the next job from the queue and run it to completion. When something on the waiting list finishes, it does not barge in. It gets put on the end of the queue and waits its turn like everything else.

ANALOGY (TEMPORARY)

A restaurant kitchen with one cook. The cook does one thing at a time, start to finish, and never stops halfway. On the wall is a timer board: the oven, the sous-vide, the driver who is out fetching the fish. None of those are the cook. The cook puts the tray in, sets the timer, and starts the next order. When a timer dings, the ding does not interrupt the cook mid-plate. The order joins the end of the ticket rail. Every "why did that print in the wrong order" question is answered by the ticket rail.

Callbacks, the thing chapter 10 promised

A callback is a function you hand to something else so that it can run it later. You do not call it. You give it away. setTimeout(() => { save(); }, 150) hands an arrow function to the browser's timer, and the browser calls it back when the time is up. addEventListener('click', fn) hands a function to the browser, which calls it whenever a finger lands. You read both in chapter 10 without having the word. That is the whole idea, and everything below is built on it.

A promise is a receipt

Callbacks alone get ugly fast: a reply that needs another request that needs another one becomes functions nested inside functions five deep. So the language added an object for "a value that is not here yet".

A promise is a receipt. You hand over your order and get a slip of paper back immediately. The slip is not the food. It is a claim ticket that ends up as exactly one of two things: resolved, the value is ready, or rejected, it went wrong and here is why. Never both. fetch hands you a receipt on the spot and the reply lands on it later.

async / await: pause this function, not the app

Working with receipts by hand is still fiddly, so there is a spelling that makes it read like ordinary top-to-bottom code. Mark a function async and you may use await inside it.

await means one precise thing, and getting it exactly right is the point of this chapter: take this function's card off the pile, put it aside with a note saying which line it was on, and let the thread go do everything else. When the receipt is paid, put the card back on the queue and carry on from that line.

Read that again against chapter 10's picture. The card leaves the stack. It does not sit on top blocking. The thread is free the instant await is reached, which is why the screen keeps redrawing, the scroll keeps scrolling, and the spinner keeps spinning while Memento waits on the AI. Nothing is frozen because nothing is being held.

Two consequences. An async function always hands back a promise, even if you wrote return 5: the caller gets a receipt, not a 5. And calling one without awaiting it, fire and forget, starts the work and moves straight on, which is sometimes what you want and sometimes the bug.

Errors are the easy part. If the awaited thing rejects, the await line throws, exactly like chapter 11's bad JSON. So the net is the same net: wrap it in try / catch. A network failure and a syntax explosion land in the same place, handled by the same four lines.

One thing await does not do: make your own code interruptible. A million-pass loop has no await in it, so nothing else runs and the page genuinely freezes. That is blocking, and chapter 1's sandbox 5 was its purest form.

ANY APP: show the wait before you wait

The order of the first four lines of any request-sending function is a user-experience decision, not a technical one. Mark the app busy. Clear the last error so a stale red message does not sit under a fresh spinner. Repaint. Only then reach for the network. Repaint before the await and the spinner appears instantly. wait() is worth a sentence. Line 71 defines it as const wait=<T>(p:Promise<T>)=>Promise.race([p,cancel]);. Two receipts go in and Promise.race hands back whichever settles first: the network, or a timer that rejects. So the await finishes when the reply lands or when the deadline passes, and a dead server can never park that card forever.

The catch is the second half. Any throw from that block, a timeout, a torn stream, a reply too big to trust, arrives here and is not re-thrown. It becomes {status:'failure', code:...}, an ordinary value. safe is an allowlist: only those seven messages get out, anything else becomes one generic code, so a raw error can never leak server detail into the app. finally runs on both paths and clears the timers.

ANY APP: await, then decide

Sending data to a database is a request like any other, and the answer matters. You await it, then read what came back and branch: accepted, rejected, or something broke. The awaited call is one line. The decision after it is the feature.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative to await is .then() chains, the older spelling of the same machinery: fetch(url).then(r => r.json()).then(data => ...).catch(...). It works identically and you will meet it in older code. Memento uses await because a function like pushNow() is a sequence of decisions, and decisions written as straight lines with ordinary if statements are readable by a human at 1am. The cost is that await makes concurrent work look sequential: await a(); await b(); takes as long as both added together when the two were independent. That is the standard performance trap, and chapter 25 shows the fix.

WORDS YOU NOW OWN
Main thread
The one finger that runs your JavaScript. There is no second one running your functions.
Queue
The line of jobs waiting for the thread. First in, first out. Nothing jumps it.
Event loop
One rule: when the thread is empty, take the next job from the queue and run it to completion.
Callback
A function you hand to something else so it can run it later. Every timer and every event listener is one.
Promise
A receipt for a value that arrives later. It ends up resolved (here it is) or rejected (here is why not). Never both.
async
A mark on a function that allows await inside it. An async function always hands back a promise.
await
Park this function, give the thread back, resume from this line when the receipt is paid. It pauses one function, not the app.
fetch
Send a request over the network. Hands you a receipt immediately, the reply lands on it later.
Blocking
Holding the thread so nothing else can run. A long loop blocks. An await does not.
Fire and forget
Calling an async function without awaiting it. The work starts, you move on, and nobody is watching whether it failed.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you say the computer only has one cook. It does not. The browser runs many threads, and this book's own sandbox proves it: every Run button sends your code to a Web Worker, a separate thread, which is why a loop that never ends can be killed without taking the page down. The native side is worse for the analogy, because React Native runs its own JavaScript thread alongside a separate native UI thread and the two pass messages. Real model: "one thread" means one JavaScript main thread per page or per app. Your code is never interrupted mid-function and two of your functions never run at the same instant, but plenty is happening beside you. And the thread is genuinely blockable: chapter 1's sandbox 5 froze solid until the timeout killed it, because await buys you nothing against your own slow code. A second, smaller break: the ticket rail is really two rails. See the rabbit hole.

RABBIT HOLE: why the promise printed before the timer

In sandbox 2, D printed before C even though the timer said 0. There are two queues. Settled promises go on the microtask queue; timers, clicks and network callbacks go on the task queue. After every single task, the thread drains the entire microtask queue before touching the next task. So promises always beat timers, and a promise that schedules another promise that schedules another can starve the timers completely and freeze the page while technically never blocking.
