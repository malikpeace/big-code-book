The terminal is a conversation

Every line you type is the same shape: the name of a program, then what to give it. It answers on one channel, complains on another, and leaves behind a number saying whether it worked. Learn those four facts and the black window stops being a threat.

The idea

The window is not the thing. The thing is a program called a shell, and yours is named zsh. It does four jobs, over and over, forever: read a line, find the program you named, run it with the rest of the line handed over, print what came back. Then it shows the prompt again and waits.

So a command is a program plus arguments. In head -20 js/33-action-shim.js, the program is head, and it gets two arguments. The ones starting with a dash are flags, the dials on the program. The rest is usually what to work on. That is the entire grammar. There is no second grammar to learn later.

How does the shell find head? There is a list of folders it searches, in order, and that list lives in a setting called PATH. which head tells you which one it found:

$ which node
/opt/homebrew/bin/node

That is where your Node came from. If which prints nothing, the program is not installed, or it is not in any folder on the PATH. This is the whole explanation for "command not found", and it is also why a fresh Mac cannot run node until something installs it and puts it on the list.

Now the answers. A program talks back on two separate channels. Standard output, stdout, is the answer you asked for. Standard error, stderr, is the complaints. They both land in the same window, which is why nobody notices there are two, until you send one somewhere and the other keeps showing up.

And when it finishes, the program hands back a number nobody shows you: the exit code. Zero means it worked. Anything else means it did not, and the number says roughly what went wrong. Ask for the last one with echo $?. This tiny number is what makes automation possible: it is how your deploy robot knows the tests failed, and how && decides whether to run the next command.

ANALOGY (TEMPORARY)

A very literal clerk at a counter. You slide a slip across: the name of the form you want, then the details. The clerk does not interpret, does not check whether you meant something else, and does not care that you are in a hurry. He returns the document on one tray and any complaint on a second tray, and stamps the slip with a number: 0 if he did it, something else if he did not. Nothing happens until you slide the slip. Nothing extra ever happens.

The commands that pay rent

You met six in chapter 5. Here are seven more, and then you are done collecting.

You typeIt means
head -5 file.js / tail -5 file.jsFirst five lines. Last five lines. Tail is how you watch a log.
grep -n "streak" app.jsPrint every line containing streak, with its line number.
grep -rn "persistState" jsThe same, recursively through a whole folder. This is the command that reads a codebase.
find . -name "*.css"Find files by name instead of by contents.
echo $HOMEPrint something. Mostly used to look inside a setting.
ls | wc -lA pipe. Send the stdout of the left into the right. Here: count the names.
ls > files.txtA redirect. Put the stdout in a file instead of on screen.

Two warnings about that last one. > overwrites the target file completely, with no prompt and no undo, so never point it at a file you care about. >> adds to the end instead. And note that only stdout gets redirected, which is why errors still appear on screen when everything else has gone quiet. Send stderr away separately with 2>/dev/null, where 2 is the channel number and /dev/null is the bin.

When you do not know a program's flags, ask it. Most answer --help with a short list. man grep opens the full manual, and q quits it. Reading two lines of --help beats guessing every time.

Settings the shell hands down

An environment variable is a named value the shell hands to every program it starts. echo $HOME prints yours, echo $SHELL proves you are in zsh. Set one with export CLARITY_MODE=1, and every program started from that window can read it.

This is exactly how secrets travel. A key never gets typed into code, where it would be saved, committed, pushed and public forever. It gets put in the environment of the one server that needs it, and the code asks for it by name at the moment it runs. Memento's proxy does precisely this, in one line: Deno.env.get('ANTHROPIC_API_KEY'). Chapter 19 does the whole subject.

Break it, twice

First, a failure. Type ls /nope, then echo $?.

$ ls /nope
ls: /nope: No such file or directory
$ echo $?
1

The message came out on stderr. The 1 is the exit code. Run ls on a folder that exists, ask again, and you get 0. You have now seen the number your deploy robot reads on every push.

Second, a runaway. Type while true; do echo hi; done and watch the window fill up forever, because you told it to and the machine has no opinion about that. Hold control and press C. It stops. Ctrl-C is the stop button, and it is the single most useful key in the Terminal: it interrupts whatever is running and hands you back the prompt.

Ctrl-C only reaches the program in front of you. Something running in the background, like a forgotten local server holding onto a port, needs finding first. ps lists running processes with their id numbers, and kill 4821 asks that one to stop. Memento's own launcher does this every time you start it, which you are about to read.

See it

A shell in fifteen lines. It splits a line into a program and arguments, looks the program up, and returns two channels plus an exit code. The real one does more, but not differently.

const PROGRAMS = { echo: (args) => ({ out: args.join(" "), err: "", code: 0 }), ls: (args) => args[0] === "/nope" ? { out: "", err: "ls: /nope: No such file or directory", code: 1 } : { out: "index.html\ncss\njs", err: "", code: 0 } }; function run(line) { const [name, ...args] = line.split(" "); // program first, then arguments const program = PROGRAMS[name]; // this lookup is what PATH does if (!program) return { out: "", err: "zsh: command not found: " + name, code: 127 }; return program(args); } for (const line of ["echo hello there", "ls memento-app", "ls /nope", "lz"]) { const r = run(line); console.log("$ " + line); if (r.out) console.log(r.out); if (r.err) console.log("[stderr] " + r.err); console.log("[exit code] " + r.code); }

Predict the four blocks before you press Run. Then look at the last one: a name the lookup cannot find comes back 127, which is the real code zsh uses for "command not found". Break it yourself by deleting the if (!program) line and running it again. The crash you get is the machine being literal, exactly as in chapter 1.

Now in Memento

ANY APP

Nobody remembers long commands. Two ways to stop trying.

Name them in the project. A package.json has a scripts section: short names for long commands, kept next to the code, so every human and every robot runs the same thing.

Save them in a file. A file of shell commands is a script. Make it runnable and it is a program like any other, indistinguishable from the built-in ones as far as the shell is concerned.

MEMENTO

The native app names its commands:

  "scripts": {
    "start": "expo start --dev-client",
    "ios": "expo run:ios",
    "android": "expo run:android",
    "typecheck": "tsc --noEmit",
    "test": "jest --runInBand",
    "check": "npm run typecheck && npm test"
  },
memento-native/package.json:9-16 (native pin 93bfa796)

Read the last one. npm run check is the type checker followed by the tests, and && means "only if the first one exits 0". A type error means the tests never run and the whole thing exits non-zero. That is the gate CI reads.

And the thing you double-click to see the web app is a saved command:

OLD_PID=$(lsof -ti tcp:$PORT 2>/dev/null)
if [ -n "$OLD_PID" ]; then
  kill "$OLD_PID" 2>/dev/null
  sleep 1
fi
Open Memento (new modular).command:10-14 (repo root, native pin 93bfa796)

Everything in there is this chapter. lsof -ti tcp:8090 asks which process is holding that port, and its stdout is captured into a variable. 2>/dev/null throws the complaints away. kill stops the old server so the new one can have the port. That file is not magic, it is five commands somebody got tired of typing.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative to a launcher script is opening index.html straight from the disk with a double click. It works, until it does not: the browser then keeps serving you yesterday's JavaScript out of its cache, and you spend an hour debugging a bug you already fixed. The launcher exists because that happened, so it starts a tiny local server that sends no-cache headers and kills any stale one first. The cost is a Terminal window you have to leave open. The alternative to named npm scripts is everyone typing tsc --noEmit from memory, where everyone includes two AI agents and a CI robot, and one of them types it slightly differently.

WHERE TODAY'S ANALOGY BREAKS

Breaks when: you decide the clerk is part of the building. The shell is just another program, with a name and a version, and it can be swapped: zsh is the Mac default now, bash was before it, and servers run either. Its own rules are a full programming language, which is why while true; do echo hi; done is a legal thing to type at a prompt, and why a shell script can have real bugs. The counter is also not one queue: programs can run in the background, and their output arrives in your window while you type something else. Real model: the shell is a program that turns a line of text into a new process with its arguments, its environment, and three streams attached (input, output, errors), then waits for that process to end and keeps its exit code. Everything else, pipes, redirects, loops, scripts, is arrangements of that one move.

RABBIT HOLE: why a script needs the ./

Running a script in the folder you are standing in takes ./launch.sh, not launch.sh, and the reason is security. The current folder is deliberately not on the PATH. If it were, downloading a folder containing a file called ls and then typing ls would run a stranger's program instead of the real one. Making you write ./ forces you to say out loud that you mean this file, here. The same instinct is why chapter 5 told you never to run an unknown command in a folder you are only visiting.
