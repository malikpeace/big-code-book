Errors, logs, stack traces, debugging

An error message is not the computer being rude. It is the computer handing you a written statement with the address of the crime on it. Once you can read one, most bugs stop being scary and start being boring, which is exactly what you want.

LAST TIME

A React component is a function that takes props and returns a description of what to draw. Hooks are how that function remembers things between redraws. React Native runs the same idea against real native views instead of HTML, which is why Memento's rebuild can share its logic and still feel like an iPhone app.

Quick check

What is the call stack, in one sentence, and what happens to it when a function returns?
A pile of index cards, one per function currently in progress, with only the top one running. When a function returns, its card is thrown away and the machine resumes the card now on top, exactly where it paused. Chapter 10.
Why does Memento's phone never call Anthropic directly?
Because the API key would have to travel to the phone, and anything on the phone can be read. The phone calls Memento's own edge function, which holds the key on the server and forwards the request. Chapter 16.
In a state to render to events app, what is the one thing you must never do?
Edit the screen directly and skip state. The moment the screen holds a fact that state does not, the next redraw wipes it and the two drift apart. Chapter 14.

The idea

Debugging is not a talent. It is a routine, and the routine is short. Most of what makes it feel like magic when an engineer does it is that they have read ten thousand error messages and you have read four.

Start with the fact that there are three kinds of broken, and they fail in three completely different places.

KindWhen it is caughtWhat you see
Syntax errorBefore a single line runsNothing works at all. The file was never even understood.
Runtime errorWhile running, at the exact bad momentA red line naming a type problem, and everything after it is dead.
Logic errorNever. Nothing catches it.A clean console and a wrong answer on the screen.

A syntax error means the machine could not read the file. A missing comma, an unclosed brace. Nothing in that file exists, not one function, because the browser parses the whole thing before running any of it. That is why one typo in state.js gives you a blank app and a second, confusing error in app.js. Cheap to find: the tools point at the character.

A runtime error means it read fine, ran, and hit something impossible. undefined is not a function. Cannot read properties of null. Almost always the same story: you expected a thing to be there, it was not, and you treated the nothing like a thing. The message is accurate and people still skim it.

A logic error is the expensive one. No red line, no trace, no alarm. Only a human noticing the streak says 0 on a day they completed. Every hour spent learning to read errors is really training for this one, because the only tool that finds a logic bug is a person deciding to check an assumption.

ANALOGY (TEMPORARY)

Three ways a recipe fails. The card is water damaged and unreadable, so nobody cooks anything: syntax. The card is readable, the cook gets to step four, and there are no eggs in the fridge: runtime, and the cook stops mid dish holding a bowl. Or the card says salt where it meant sugar, the cook follows it perfectly, dinner is served, everyone smiles, and the cake is disgusting: logic. Only the third one needs somebody to taste it.

When a runtime error happens, the machine photographs the call stack from chapter 10 and prints it. That photo is the stack trace. Six things are in there, and every one is useful.

  1. The first three lines are a quotation: file, line, the actual source line, and a caret under the exact spot. Free evidence, and people scroll past it.
  2. TypeError is the family. A value was the wrong kind of thing for what you did to it.
  3. Cannot read properties of null (reading 'toISOString') is the sentence that solves the bug. Something was null and the code asked it for toISOString. You know the shape of the fault before opening a file.
  4. The at lines are the pile, top card first. dayKey broke, completeToday called it, onHoldFinished called that. Read down and you read backwards in time.
  5. file:3:15 is line 3, column 15. On a line with four calls on it, the column says which one.
  6. The bottom lines say node:internal. Not your code, the machinery that started your program. The useful line is the first one naming a file you or your agent wrote. In a browser those frames say things like HTMLButtonElement.dispatchEvent, ignorable for the same reason.

The routine

Reproduce first. A bug you cannot trigger on demand is a rumour. Find the exact steps that make it happen every single time, and write them down before touching code. "It just broke" is never the full story. The full story is "on a fresh account, after completing once, reload and the streak reads 0". Half of all bug reports die right here, because the bug turns out to be one stale browser tab.

Then isolate. Cut the problem in half. Comment out the bottom half of the function. Still broken? It is in the top half. This is bisecting, and it works on anything with a middle: lines in a function, files in a load order, commits in a history. Ten rounds of halving searches a thousand possibilities. Guessing searches one.

Log what you assume. console.log is a flashlight, and the trick is to aim it. Print the specific thing you are certain about. "lastCompleted is yesterday's date at this point" is an assumption; print it, and half the time it is null and the bug is over in nine seconds. The fault is never where you are sure it is not, which is exactly why you print the thing you are sure about.

The console is the app talking to you: every log an agent left behind, every browser warning, every uncaught error. Memento's build rule is one line about this exact window: After edits, verify in a browser and confirm ZERO console errors before pushing. CLAUDE.md:64 (web pin ca8afc8) Not "few". Zero. A console with three errors you have learned to ignore is a console where the fourth one hides.

One more split. Browser logs are yours alone, on your device, gone on reload. Server logs are the only record of what happened to a user you will never meet. When Memento's AI call fails for somebody in another country, nothing appears in your console; the evidence is in the Supabase dashboard's logs for that edge function, and in whatever the function chose to write down. A server that swallows its errors silently is a server you cannot debug, which is why Memento's proxy records upstream 500s before it answers the phone. supabase/functions/ai-proxy/index.ts:184-186 (web pin ca8afc8)

Catching, on purpose

A runtime error is also called an exception, and code can raise one deliberately with throw. The machine then stops that function and discards cards off the pile one by one, looking for a try/catch. Find one and the catch runs and the program carries on. Find none and the error reaches the top, which is when the trace gets printed and the app dies. That is why try around one risky line is a fence, not a bandage: this can fail, here is the plan.

ANY APP: never hand a raw error to a user

An error message is written for the person who wrote the code. It can contain file paths, internal names, parts of the request, sometimes a token. Show it to a user and you have confused them and leaked your insides at once. The standard move: keep a short list of failure words you are willing to say out loud, and turn everything else into one generic word.

MEMENTO: the allowlist in transport.ts

ANY APP: the failure you know is coming

Saving to the browser's storage can fail: disk full, private mode, the phone decided today is the day. You cannot prevent it, so you catch it, work out whether it is the failure you understand, and tell the user once instead of forty times.

ANY APP: the server decides what the client hears

When your server calls somebody else's server and that call fails, you choose: forward their error body, which is easy and leaks, or replace it with your own sentence. Their error body can echo your request, which contains your user's words and your own prompt.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative is to pass the real error through to the screen, which plenty of apps do, and it is genuinely better for debugging: you would see the provider's actual message instead of guessing. The price is that anybody can pick at a failing endpoint and read internals out of it, and that a user mid Clarity session gets a wall of JSON instead of a sentence. Memento pays for safety with a worse view. invalid-or-unavailable-response literally means "something we did not plan for", and the only place to learn what is the server log. That trade is why the proxy records its 500s before answering, and why the allowlist is seven words and not two.

WORDS YOU NOW OWN
Syntax error
The file could not be read at all, so nothing in it exists. Caught before a single line runs. Usually one character.
Runtime error
The file ran and hit something impossible, usually treating a null or undefined like a real thing. Stops the code at that exact point.
Logic error
It ran fine and did the wrong thing. No alarm, no trace. The only detector is a human checking the answer.
Exception
An error object thrown up through the call stack. Each card is discarded until a catch is found, or until it reaches the top and the app dies.
try / catch
A fence around a line that can fail, plus the plan for when it does. finally runs on both paths, which is where cleanup goes.
Stack trace
The printed call stack at the moment of the error. Top line is where it broke, each line below is who called whom, file:line:column. The useful line is the first one naming a file you wrote.
Console
The window where the app talks to you: logs, warnings, uncaught errors. Memento's rule is zero errors in it before any push.
Reproduce
The exact steps that trigger the bug every time. Written down before any code is touched. Without it you cannot tell a fix from a coincidence.
Bisect
Cut the search space in half, test, repeat. Works on lines, on files, and on git history. Ten halvings beat a thousand guesses.
Debugging
Reproduce, isolate, log the thing you assume, fix, confirm. A routine, not a gift.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: the kitchen has more than one cook. The recipe picture assumes one thing at a time, so a failure gives you one clean trace pointing at one line. Chapter 12's async world does not work like that. When an error happens inside an await, or inside a callback the browser invoked minutes later, the card that started it all is long gone from the pile and the trace can show a handful of frames with nothing recognisable in them. It is also why an error thrown inside a promise nobody is waiting on can vanish without printing anything. Real model: a trace shows what was on the stack at that instant, not the story of how the app got there. For async faults you stop trusting it to name the culprit and go back to reproduce, log, bisect, which is why the routine is the thing worth memorising and not the trace format.

RABBIT HOLE: why a trace from a real user is often useless

Code that ships to a browser is usually squashed by a bundler: whitespace gone, names shortened to single letters, forty files glued into one. A trace from that file says at t (main.4f8a.js:1:20481), which names nothing. The fix is a source map, a separate file saying "character 20481 of the squashed file was line 63 of transport.ts", which error reporting tools use to rebuild a readable trace. Memento's web app ships unbundled on purpose, a real cost in other ways with this one genuine benefit: every trace from a real phone names the actual file and line. The native app, bundled by Expo, needs the source map.
