Git 1: snapshots and history

Every version of Memento that has ever existed is still on your Mac, 2,659 of them, each one a complete photograph of the whole folder. This chapter is how that works and how you look at it without breaking anything.

LAST TIME

The terminal is a conversation: every line is a program's name plus arguments, and the shell finds that program by walking PATH. Output comes back on two channels and every command ends with an exit code, where 0 means it worked. You are no longer scared of a black window.

Chapter 4 gave you five habits. The fifth one was "own the commit". What do you think that actually means?
Whatever the agent wrote, it goes into history under a message you approved, and you are the one who can say what changed and why. By the end of this chapter you will know exactly what a commit is, so that habit stops being a slogan.

The idea

Almost everyone believes a commit is a record of what changed. It is not. A commit is a complete snapshot of the entire folder at one moment: every file, in the state it was in, with the folder structure it had. Git stores the whole tree, not the edit.

That sounds insane until the second half of the trick. If a file did not change since the last snapshot, git does not store it again. It stores each file's content once, under a fingerprint of that content, and every snapshot containing that exact file points at the same stored copy. Complete and cheap. Memento has 2,659 snapshots of a folder whose web app alone is 7.8 megabytes. Real copies would be over twenty gigabytes. The whole history is 462 megabytes.

The snapshots are not a pile. They are a chain. Each commit records which commit came before it, its parent. Follow the parents backwards and you walk the entire life of the project, one snapshot at a time, to the first one. That chain is the history. Nothing in it is ever edited. Things only get added to the end.

ANALOGY (TEMPORARY)

Save-game slots, with one extra rule. Every save is a full save of the entire world, not a list of what you did since last time, so loading any slot gives you the world exactly as it was. The extra rule: each save writes down which save you were playing when you made it, so the slots form a line you can walk backwards. And undoing does not delete a save. It makes a new save with the thing undone. Nothing ever comes off the shelf.

Now the part that confuses everybody. When you work with git there are three different places your work can be, and they are genuinely separate:

  • The working folder. The actual files on your disk, the ones your editor opens and your app runs. You change these all day.
  • The staging area, also called the index. A waiting room. It holds the exact version of each file that will go into the next snapshot. Putting a file in the waiting room is git add.
  • The history, which lives in a hidden folder called .git at the top of the project. Every snapshot ever taken is in there. git commit takes everything in the waiting room and writes it in as a new snapshot. A project folder plus its .git folder is a repository, or repo.

The difference between any two of those places, printed as removed and added lines, is a diff. And HEAD is git's word for the snapshot you are currently standing on, which for now is simply the newest one.

Editing a file changes the first place only. Nothing reaches history until you add, then commit. That two-step is not bureaucracy. It lets you say "these four files are one coherent change, and those two I am still messing with are not part of it". Hold that thought: it is the entire reason for a rule you have enforced in Memento for a year.

The hash, and why it looks like that

Every commit has an id that looks like 93bfa79698c797f48bd3a45add06fb17ff31ca7a. That is a hash: a fingerprint calculated from the snapshot's contents, including the parent's id and the message and the author and the time. Feed identical contents in, get the identical fingerprint out. Change one character anywhere and you get a completely different fingerprint.

Two consequences. The id is not a counter, so there is no "commit number 400"; ids identify, they do not sort. And because the fingerprint includes the parent's fingerprint, you cannot quietly rewrite an old snapshot: change anything back there and every id after it changes too. History is tamper-evident by construction.

In practice nobody types forty characters. The first seven or eight are enough to be unique in a project this size, which is why you see ca8afc8 and 93bfa796 in Memento's own notes.

See it

Git in miniature. Commits are objects with a parent pointer. Watch two things: the history only ever grows, and undoing a change makes a new snapshot rather than removing an old one.

// A pretend git. Each commit holds the WHOLE folder, plus its parent. const history = []; function commit(message, folder) { const parent = history.length ? history[history.length - 1].id : null; const snap = { id: "c" + (history.length + 1), message, parent, folder: { ...folder } }; history.push(snap); return snap; } let folder = { "app.js": "start()", "README": "Memento" }; commit("first snapshot", folder); folder["app.js"] = "start(); trackStreak()"; // edit the working folder commit("add streak tracking", folder); folder["app.js"] = "start()"; // the undo commit("revert the streak tracking", folder); console.log("snapshots kept:", history.length); history.forEach(c => console.log(c.id, "parent:", c.parent, "|", c.message, "|", c.folder["app.js"]));

Three snapshots, not one. The middle one still holds the streak code, which is why a revert is safe: you can go and read the thing you undid. Now the second half of the claim, that a full snapshot is not a full copy.

// Content-addressed storage: store each unique file ONCE, under a fingerprint. const store = {}; // fingerprint -> content function put(content) { const fp = "f" + [...content].reduce((a, ch) => (a * 31 + ch.charCodeAt(0)) % 99991, 7); store[fp] = content; // writing the same content twice is free return fp; } const snapshots = []; function snap(folder) { const tree = {}; for (const name in folder) tree[name] = put(folder[name]); snapshots.push(tree); // the snapshot is a list of fingerprints } snap({ "app.js": "start()", "README": "Memento" }); snap({ "app.js": "start(); trackStreak()", "README": "Memento" }); snap({ "app.js": "start()", "README": "Memento" }); console.log("snapshots:", snapshots.length); console.log("unique file contents actually stored:", Object.keys(store).length); console.log("README fingerprint is the same every time:", snapshots.map(s => s["README"]).join(" "));

Three complete snapshots, three stored file contents, not six. The README was written once and pointed at three times, and the third snapshot's app.js reuses the first one's fingerprint because the content came back to identical. That is git, minus a million lines of hard engineering.

ANY APP

The one-line summary of history is git log --oneline. Each line is a short hash and the commit's subject. It reads newest first. This is the single most useful git command in the world, and it is completely safe.

To look inside one snapshot, git show <hash>. Add --stat and you get the header plus a count of which files moved and by how many lines, without a wall of code.

The -C <folder> flag means "run this as if you were in that folder", so you never have to cd into one you must not disturb.

Why Memento bans git add -A

This is the rule you wrote, and now you can read it properly. Run grep -n 'git add' ~/Downloads/MEMENTO/CLAUDE.md and you get line 73:

- **After a meaningful change:** commit ONLY your own files: `git add <your specific files> &&
  git commit -m "<what changed>" && git push origin main`. **NEVER `git add -A`**
  (other agents share this tree; a blanket add scoops up their half-done work
  and causes duplicate features).
CLAUDE.md:73 (line broken here to fit the page; it is one line in the file)

git add -A means "put every changed file in the whole project into the waiting room". On a solo project, convenient. In Memento it is a loaded gun, because the working folder is shared. While Fable is halfway through a screen, its unfinished files sit in that folder. If Codex runs git add -A then, they go into the waiting room, get committed under Codex's message, and are pushed. A broken half-feature is now in history under a message that does not describe it, and the next agent to pull gets it. The duplicate features the rule complains about are exactly that: half a thing committed twice, from two directions.

The staging area is the defence. Naming your files is how you say "this change is mine, and it is these four files". The rule is not tidiness. It is the only mechanism git gives you to stop two authors in one folder eating each other's work.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The obvious alternative is one working copy per agent, so nobody shares a folder and git add -A is harmless. Memento does that for the native rebuild: the migration plan puts Codex in a separate worktree at ../MEMENTO-codex while Fable stays in the Downloads checkout. It costs disk space, a second checkout to keep current, and remembering which copy you are looking at. For the web app the agents kept one tree and paid with a rule instead. Both are real choices. What does not work is one tree and no rule, which is what most people do.

WORDS YOU NOW OWN
Commit
A snapshot of the whole folder, with a message, an author, a time, and a pointer to the snapshot before it. Not a record of changes.
Repository (repo)
A project folder plus its hidden .git folder containing every snapshot ever taken of it.
Working folder
The real files on disk that you and the agents edit. Nothing here is in a snapshot until you add and commit.
Staging area (the index)
The waiting room. It holds the exact file versions that will go into the next snapshot. git add <file> puts one in.
Hash
A commit's id: a fingerprint of the snapshot's contents and its parent's id. Same contents, same fingerprint. Change anything and every id after it changes too.
Diff
The difference between two versions of a file, as removed and added lines. git diff: working folder against waiting room. git diff --staged: waiting room against the last snapshot.
HEAD
Git's word for the snapshot you are currently standing on. Chapter 8 makes it move.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you picture 2,659 complete copies of the folder, or assume every save survives forever. Git stores each unique file content once and every snapshot points at the shared copies, which is why the history is 462 megabytes instead of twenty gigabytes. And a snapshot nothing points at any more, because a label moved or a branch was deleted, becomes unreachable and is eventually swept away by git's garbage collector. Real model: a content-addressed database of objects, where a commit names a tree, a tree names file contents by fingerprint, and reachability from a label keeps an object alive. Chapter 8 brings the labels.

RABBIT HOLE: what is actually inside .git

Four kinds of object, all stored by fingerprint. A blob is one file's contents with no name. A tree is a folder listing: names plus the fingerprints they point at, including other trees. A commit names one tree, its parents, an author, a time and a message. A tag names a commit with a human label. On top of that sits a small folder of refs, which are plain text files each containing one hash, and those are branches. That is the entire design. Everything else in git, every command and every flag, is manipulation of those four object types and those one-line ref files. Linus Torvalds wrote the first working version in about ten days in 2005, which chapter 3 put on the timeline.
