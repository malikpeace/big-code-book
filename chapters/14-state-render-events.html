State, render, events: how data flows through a screen

One rule holds every frontend together: the data is the truth and the screen is a photograph of it. Break that rule in one place and the app starts lying to your users about their own streak.

LAST TIME

HTML declares what exists, CSS paints it, and the browser turns the file into a live tree called the DOM. JavaScript changes the screen by changing that tree, with querySelector, textContent, and classList. Events travel up the tree, which is why Memento calls e.stopPropagation() when a tappable thing sits inside another tappable thing.

Quick check

You tap a button inside a card and two handlers fire. What happened, and how do you stop it?
The event bubbled up from the button to the card. e.stopPropagation() in the button's handler stops the trip.
const state = { streak: 4 }, then state.streak = 5. Legal?
Yes. const locks the name, not the object behind it. Only state = somethingElse is refused, and that distinction is about to matter a lot.
Why does a slow AI reply not freeze Memento?
await parks that job and hands the single thread back, so taps keep being served. The reply is picked up later from the queue.

The idea

An app is a loop with three stops, and it only ever runs clockwise.

State is everything the app currently knows: the streak, the north star, whether today is done. One object, one place. The screen is drawn from it, and drawing it is called a render. The user does something, that changes state, that redraws the screen. Every frontend framework ever written is an argument about the third arrow.

The rule underneath it has a name: single source of truth. For any fact, exactly one place is allowed to be right about it. Everything else is a copy, a view, a photograph. If the streak lives in the state object, then the number on screen is not the streak. It is a picture of the streak, and pictures do not get edited.

ANALOGY (TEMPORARY)

A shop with a stockroom and a window display. The stockroom is state: it is the only honest answer to "how many do we have". The window is the screen. When stock changes, you redo the window from the stockroom. What you must never do is walk outside, put an extra box in the window, and feel good about it. Now the window says twelve and the stockroom says eleven, nobody notices until someone tries to sell the twelfth, and the customer is the one who finds out.

The two ways to do the render arrow

Imperative rendering means you do the work: find the element, set the text, toggle the class. You are telling the browser the steps. It is what the whole web ran on for twenty years, it needs no tools, and it is exactly what Memento's web app does today.

Declarative rendering means you write one function saying what the screen looks like for a given state, and a framework works out which bits of the real screen must change. You describe the destination, not the route. React does this, which is why the native rebuild has no querySelector in it anywhere.

Neither is the good one. Imperative is a hammer and declarative is a nail gun, and the nail gun needs a compressor.

Drift, the bug this chapter exists to prevent

Drift is when the screen and the state stop agreeing, and it happens one way: somebody changed the screen without changing state. The number goes up, the user is happy, the state object still says four, and nothing looks wrong until the app redraws from state, which it will, on the next page load. Then the streak walks backwards and the user tells you your app ate their progress.

Drift never announces itself. No error, no red line, no crash. The only defence is the rule: every handler changes state, then calls render. Never the screen directly.

Debounce: wait a beat, then save once

State that only lives in memory dies when the tab closes, so it gets written to storage. But typing fires an event per keystroke, and forty writes to do the work of one is waste. Debouncing is the fix: start a short timer instead of saving, and if another change arrives first, cancel and restart it. The save happens once, a beat after the person stops. Memento waits 150 milliseconds. So does Memento Jr, because it was copied from Memento.

See it

Three versions of the same tiny app. The first obeys the rule.

<h1 id="streak"></h1> <button id="go">Complete today</button> <script> var state = { streak: 0, done: false }; // the only truth function render() { // screen drawn FROM state document.querySelector("#streak").textContent = state.streak + " day streak"; document.querySelector("#go").textContent = state.done ? "Done" : "Complete today"; } document.querySelector("#go").addEventListener("click", function () { state.streak = state.streak + 1; // 1. change state state.done = true; console.log("state:", JSON.stringify(state)); render(); // 2. redraw from it }); render(); // first paint </script>

Read the click handler out loud: change state, then render. Two lines, in that order, forever. Now the same button written the way it goes wrong.

<h1 id="streak">0 day streak</h1> <button id="go">Complete today</button> <button id="reload">Pretend to reload the page</button> <script> var state = { streak: 0 }; var out = document.querySelector("#streak"); document.querySelector("#go").addEventListener("click", function () { // THE BUG: the screen is edited, state is never told. var shown = parseInt(out.textContent, 10) + 1; out.textContent = shown + " day streak"; console.log("screen says " + shown + ", state.streak is still " + state.streak); }); document.querySelector("#reload").addEventListener("click", function () { out.textContent = state.streak + " day streak"; // any redraw uses state console.log("redrew from state. every tap you made is gone."); }); </script>

Tap the first button five times. It works. It looks perfect. Now tap the second one, which does nothing more than what a real page load does, and watch five days of someone's life disappear. That is drift, and that is why it is worth a whole chapter.

The third version never touches an element by hand. It rebuilds the whole screen from state every time, which is the idea a framework is built on.

<div id="root"></div> <script> var state = { northStar: "ship the native app", streak: 3, done: false }; var root = document.querySelector("#root"); // A pure function: same state in, same HTML out. No side effects. function view(s) { return "<h3>" + s.northStar + "</h3>" + "<p>" + s.streak + " day streak</p>" + "<button id='go'>" + (s.done ? "Done" : "Complete today") + "</button>"; } function render() { root.innerHTML = view(state); // throw it all away, rebuild document.querySelector("#go").addEventListener("click", function () { state = { ...state, streak: state.streak + 1, done: true }; // a NEW state object console.log("new state:", JSON.stringify(state)); render(); }); } render(); </script>

Two things to notice. view is pure, so you could test it with no browser: hand it a state, check the string. And the handler builds a new object rather than editing the old one, which is how a framework tells what changed by comparing before and after. Real React compares descriptions of the screen, it does not glue HTML strings. Gluing user text into innerHTML like this is also an injection hole, which chapter 25 will make you care about.

Now in Memento

ANY APP

One object holds everything. One function saves it, debounced. Screen-updating functions read that object and push its values into elements. Nothing else is allowed to be right about the data.

Saving is where truth leaves memory and becomes a key in storage, so it is the line that decides what survives a reload.

The declarative half: the native rebuild

The native app keeps Clarity's flow in a reducer, a pure function that takes the current state and an event and returns the next state. It never touches a screen. It cannot, there is nothing to touch.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

Memento's web app is imperative because in 2026 it was one person and an agent shipping a screen a night, and a framework is a build step, a bundler, a dependency tree, and a week of setup before the first pixel. Plain files load instantly and can be edited on the Mac with no tooling, which is the whole reason the app exists at all. The bill arrived later: 67,000 lines, hundreds of hand-wired refreshers, and the recurring class of bug where one surface updates and its twin does not. The native rebuild goes declarative for exactly that reason. The cost is real and is being paid right now in the MIGRATION folder: types, a build, a test suite, and two agents re-deriving screens that already worked.

WORDS YOU NOW OWN
State (upgraded)
The single source of truth the screen is drawn from. Events change it; the screen is never edited on its own.
Single source of truth
For any fact, exactly one place is allowed to be right. Everything else is a copy.
Render
The act of making the screen match state. In Memento's web app, a few hundred small functions. In the native app, one description per component.
Imperative rendering
You find the element and change it. No tools needed, and you can forget a spot.
Declarative rendering
You describe the screen for a given state and a framework works out the changes. Needs a build; cannot forget a spot.
Drift
Screen and state disagree because something edited the screen directly. Silent until the next redraw, then it eats the user's data.
Debounce
Wait a beat, then do it once. Memento's saves wait 150ms so forty keystrokes cost one write.
Reducer
A pure function taking state plus an event and returning the next state. Testable with no screen and no phone.
Component / JSX
A reusable piece of screen described as a function of its inputs / the markup-shaped syntax used to write that description.
localStorage (upgraded)
Key-value storage in the browser, strings only, about 5 MB per site. Can throw when full or in private mode, so every write is wrapped.
Assertion
A statement in the code that must be true, which complains loudly when it is not. Your cheapest early warning.
Boundary check
Asking what happens at the edges: empty, zero, negative, enormous. Where most real bugs live.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: there is more than one stockroom. A real app has state in memory, state in localStorage, state on the phone's disk, and state in a Postgres row, and they can all disagree at once, usually because the user has two devices. The shop picture has no answer for that, because a stockroom cannot be in two cities. Real model: a chain of copies with rules about which one wins, which is what sync is and why 12-cloud-sync.js exists. Memento's database goes as far as refusing a write that would blank a real person's state, because it does not fully trust the client's copy. That is chapter 17. The second break is smaller: the shop's window is drawn only when stock changes, but a real screen also redraws for reasons that have nothing to do with state, like rotating the phone. State is the source of truth, not the only trigger.

RABBIT HOLE: why the native reducer never edits state in place

{ ...s, chunk: ... } builds a new object rather than changing the old one. That is immutability, and it exists for two reasons. Comparing is cheap: React can check whether the object is a different object, which is one comparison instead of walking every field. And chapter 11's aliasing bug becomes impossible, because nothing holds a reference to something that can change underneath it. The cost is a new object per event, thousands of them, which the engine throws away almost for free. This is the trade every modern frontend makes: spend a little memory to delete a whole category of bug.
