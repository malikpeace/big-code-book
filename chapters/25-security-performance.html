Security and performance, the junior version

Two subjects that sound like specialist work and are one habit each. Security: decide where you stop believing what you are told. Performance: measure before you touch anything.

LAST TIME

A test is an executable expectation, written once and re-run forever. Unit, integration and end to end answer different questions, and coverage measures how much code ran, not whether it was right. Memento's native side has a runner and a test that uses the frozen web code as the oracle; the web side has no runner at all.

Quick check

Why is Memento's Supabase anon key sitting in a public file, while the Anthropic key is not?
The anon key is a publishable credential whose authority was cut down on purpose. The API accepts it, but the database role behind it has almost no grants, and Row Level Security decides per row who may read what. The Anthropic key is a permission: anyone holding it can spend Memento's money. So it lives in the edge function's environment and never reaches a browser.
A request comes back with status 429. What does the app now know?
Too many requests. The server understood fine and refused on purpose, so retrying immediately is the wrong move. Memento's native transport maps that status to the code rate-limit so the UI can say something human instead of "error".
What does a migration do that editing the database by hand does not?
It is a dated, forward-only file in git. The change is reviewable, repeatable on another machine, and there is a record of when the promise changed. Memento has 33 of them.

The idea, part one: security is a boundary question

Every app has a line running through it. On one side is code you control. On the other is everything a stranger can touch: the phone, the browser, the network, the request body, the headers, the URL. That line is a trust boundary, and almost every security bug is one sentence: someone believed something that arrived from the far side of it.

The far side includes your own app. Memento's JavaScript in Safari feels like yours because you wrote it. It is running on a computer a stranger owns, and they can open the developer tools, edit any value, and send whatever they like to your server. Anything the phone sends can be forged. The button that says "I am a paid user" is a claim, not a fact.

ANALOGY (TEMPORARY)

A nightclub. Inside, nobody checks anything, because getting in was the check. The door is the trust boundary. The bouncer does four things and only four: is this person who they say (authentication), are they on the list for this room (authorization), is that bag a reasonable size (validation), and how many people are already inside (rate limit). A bouncer who lets someone in because they said "I was here last week, mate" is not a bouncer. And if the guest list system goes down, a good bouncer stops the queue. He does not wave everyone through.

Four habits sit on that boundary. They cover most of what a junior engineer is expected to know.

Validate at the edges. The first thing the server does with a request is check its shape: size, type, range. Not because users are hostile, but because the check is cheap and the alternative is your code discovering the problem twenty lines deeper, holding half a write. Validation means refusing early and saying why, in one plain sentence.

Least privilege. Every key, token and database role gets the smallest power that still does the job. That is why the key that reads a table is not the key that drops it, and why Memento's browser holds a key that can only act as the signed-in user. Least privilege, in one line.

Secrets never ship. A secret is a value your code needs and must never contain. It arrives from the environment at runtime, on the server, never in git. A secret that reaches a browser is burned. Rotate it, do not hide it.

Rate limits that fail closed. A rate limit caps how often one caller may do an expensive thing. The interesting part is what happens when the limiter breaks. Fail closed: if I cannot tell whether you are over the limit, the answer is no. Fail open is how a database blip becomes an unbounded bill.

The idea, part two: performance is a measurement question

Slow software is a feeling. Optimising is a change. The gap between them is where engineers waste weeks, because the part you think is slow is almost never the part that is slow. The rule is blunt: measure first, change second, measure again.

Two words keep you honest. Latency is how long one thing takes, from the user's finger. Throughput is how many fit in a second. They trade against each other: batching raises throughput and can make one person's wait longer.

After that, the same four suspects turn up over and over.

  • The N+1 query. The code asks the database once for the list, then once more for each row. Thirty rows, thirty one round trips. One query for everything is usually far faster and looks almost identical in the code. The most common real performance bug in web apps.
  • Bundle size. Every kilobyte the phone downloads is time before the first pixel. The one number that predicts how an app feels on a cheap phone.
  • Caching. Keep the answer so you do not compute or fetch it twice. Caching turns a slow thing into a fast thing and introduces exactly one new problem: knowing when the kept copy is stale.
  • Debouncing. When something fires constantly, wait for it to stop before acting. Saving on every keystroke is a hundred writes a minute. Wait 150 milliseconds after the last one and save once.

The cheap opening move, before any profiler: look at the biggest file. Size is not proof of slowness, but the file that grew to ten thousand lines is where the work accumulated.

ANY APP

The door lives in one file and everything expensive happens behind it, in a fixed order: reject the wrong origin, reject the wrong method, rate limit, then read the body with a cap on it. Rate limiting comes before parsing, because parsing a huge body is itself a cost an attacker can make you pay. When the limiter's own storage fails, the request is refused rather than allowed, so the spend control survives the outage.

ANY APP

The phone has a door pointed the other way: data loaded off the disk is untrusted too, because an older version of your own app wrote it, or someone edited it. A validator walks the saved tree, refuses anything absurdly large or deep, and strips values that should never have been stored. Saving is debounced, so a burst of changes becomes one write.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The proxy could fail open: if the rate-limit table is unreachable, let the call through so real users are never blocked by an outage. That is the friendlier choice and plenty of teams make it. It also means one database wobble removes every spend control at once, on an endpoint that costs real money per call, reachable anonymously. Memento chose the unfriendly branch and pays for it with a 503 that a real user might see during an outage. The cost is written in the file header rather than left for someone to discover on a bill.

WORDS YOU NOW OWN
Trust boundary
The line between code you control and everything a stranger can edit. Every rule that matters is enforced on your side of it.
Validation
Checking size, type and range at the door, and refusing with one plain sentence. Cheap, early, boring, and it prevents a whole category of bugs.
Least privilege
Each key, token and role gets the smallest power that still does the job, so a leak costs less.
Secret
A value the code needs and must never contain. It arrives from the environment, on the server, and is never in git or a browser.
Rate limit, fail closed
A cap on how often something expensive may happen. Fail closed means that when the limiter cannot answer, the request is refused.
Injection and XSS
Data treated as code, in a database command or in your page. Killed by passing values as values and escaping anything a human typed.
Latency and throughput
How long one thing takes, versus how many fit in a second. They trade against each other.
N+1
One query for the list plus one per row. The most common real performance bug, and it looks harmless in the code.
Bundle size
How much the phone must download before anything appears. The number that decides how the app feels on a bad connection.
Debounce
Wait for the storm to stop, then act once. Memento saves 150 milliseconds after the last change.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you picture one door. A real app has many, and the dangerous ones are the doors nobody drew: a database reachable directly with a public key, a storage bucket, a webhook, an old function still deployed. The bouncer also implies that once you are inside you can go anywhere, which is the assumption Row Level Security exists to destroy: the rule is per row, re-checked on every read. Real model: every place data crosses from something you do not control into something you do is its own boundary, with its own four checks. Chapter 26 asks the structural version: where should a rule live so it cannot be bypassed by accident.

RABBIT HOLE: why "measure first" is not a slogan

Programs spend most of their time in a small part of their code, and humans are terrible at guessing which part. The usual story is that a team spends a week making a function twice as fast, and the function accounted for two percent of the time, so the app got one percent faster and nobody noticed. There is an arithmetic law behind this: the best possible speedup from optimising one part is capped by how much of the total that part was. If a piece is 5% of the runtime, deleting it entirely buys you 5%. That is why the measurement is not a formality, it is the thing that tells you whether the work is worth doing at all. The same law is why the biggest file is a good first guess and a bad conclusion.

RABBIT HOLE: what a 500 should say

Two audiences, two messages. The user gets "something went wrong on the server", with no detail, because details are a map of your internals: file paths, library versions, table names, sometimes a fragment of a query with data in it. The log gets everything, because it is yours. Memento's native transport takes the same line from the other direction: it catches errors and only surfaces messages from a short allowlist, so an unexpected error message can never be painted onto a screen. Chapter 23 read that allowlist.
