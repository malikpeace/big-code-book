JavaScript 2: functions and the call stack

A function is a named recipe. Writing it down does nothing at all. Calling it is what runs it. Once you can see the pile of half-finished recipes a running program is holding, error messages stop being noise and start being directions.

LAST TIME

A variable is a name tag tied to one value, never a box. Every value has a type, and text that looks like a number behaves nothing like a number. const locks the name, not the object behind it, and === is the only comparison you should write.

Quick check

let best = streak; then streak = 10;. What is best?
Whatever streak was pointing at when that line ran. The two names were never linked. Assignment reads the right side once and points the left name at the result.
What does typeof "7" print, and why does it matter?
"string". It matters because a string of digits does arithmetic wrong and silently. It glues instead of adding.
What is a commit, physically?
A snapshot of the whole folder at one moment, with a message, an author, and an id. History is a chain of them, each pointing at the one before.

The idea

A function is a chunk of steps with a name on it. You write the steps once. Then anywhere in the app, any number of times, you say the name followed by brackets and the steps run.

Two words do all the work, and mixing them up is the beginner's mistake. Defining a function means writing the recipe down. Nothing happens. No step inside it runs. The machine notes the name and moves on. Calling it, writing its name followed by (), is what makes the steps run. A file full of definitions and no calls does precisely nothing.

ANALOGY (TEMPORARY)

A recipe card and a cook. The card says "carbonara: boil water, fry the guanciale, mix the eggs". Writing that card feeds nobody. The cook reading the card out loud feeds somebody. Parameters are the blanks on the card: "serves N people". Arguments are the numbers you shout at the cook when you hand the card over: "make it for four". Return is the plate coming back. And the moment the cook hands the plate over, that recipe is finished; anything written after the "hand over the plate" line never gets read.

The shape, with every word labelled:

function greet(name, streak) {     // name and streak are parameters: labels for the inputs
  const line = name + " is on day " + streak;
  return line;                     // hand this value back, and stop here
}

const message = greet("Malik", 12);  // "Malik" and 12 are the arguments

Parameters are variables, and chapter 9's model applies exactly. They are name tags, tied to the values you passed in, and they only exist while the function is running. name is not a box the string went into. It is a tag on the string you handed over.

return does two things at once and people usually only notice the first. It hands a value back to whoever called, and it stops the function on the spot. Lines below a return that has just run are dead. That second behaviour is what makes guard clauses possible, and Memento is full of them.

A function with no return still hands something back: undefined, the machine's shrug from chapter 9. This is the most common confusing moment for a beginner. You call a function, it clearly did its job, you print the result, and you get undefined. Nothing is broken. You just never said what to hand back.

The call stack

Now the picture that pays for the whole chapter. While a program runs, it keeps a pile of index cards. Each card is one function currently in progress, and holds that function's own local names and the line it is paused on.

Call a function: a new card goes on top of the pile. That function calls another: another card on top. A function returns: its card is thrown away, and the machine resumes the card now on top, exactly where it paused. The pile is the call stack, and the only card being worked on is the top one.

Two things fall out of this picture for free. First, scope: names created inside a function live on that function's card, so they are thrown away when it returns. That is why a name from inside a function is invisible outside it, and why two functions can both use a name like text without colliding. Each has its own card.

Second, a stack trace. When something breaks, the machine prints the pile top to bottom: the function that broke, then who called it, then who called that. It reads like a chain of blame, and the useful line is usually not the top one, it is the first one that names a file you wrote.

Guard clauses

Because return stops the function, the cleanest way to handle a bad input is to check for it on the first line and leave. That is a guard clause: deal with the exits at the top, then write the real work with no nesting under it. The alternative is wrapping everything in an if and drifting three levels deep. Memento's small functions almost all open with one or two guards, and once you can spot them, you can read the real intent of a function in about four seconds.

Arrow functions

There is a second spelling. function add(a, b) { return a + b; } can also be written const add = (a, b) => a + b;. That is an arrow function: parameters left of the arrow, body on the right, and with a single-expression body the return is implied. Shorter, which matters most when a function is being handed to something else as an instruction, like "when this is clicked, run this". Memento uses both styles, often within a few lines of each other.

Now in Memento

ANY APP: save, but not too often

Saving on every change is wasteful. A user typing a sentence would trigger forty writes. The standard move: cancel any save that has not happened yet, then schedule one for a moment from now. Type fast and only the last survives. Pause and it lands. Before any of that, one guard: if saving would be wrong right now, leave immediately.

MEMENTO: persistState()
function persistState() {
  if (DEMO_MODE || IS_RESETTING) return; // never write demo data, or re-write after a reset wipe

ANY APP: a function handed to something else

"When this is clicked, run this" needs a this to run. So you hand a whole function over as a value, and something else calls it later, when the event happens. This is the moment a function stops looking like a recipe card.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative is to write straight to storage every time anything changes. One line shorter, always correct, and it would make typing in the note editor stutter on a real phone, because every write converts the entire state object to text first. The timer means a burst of forty changes costs one write. The price is a 150 millisecond window where a hard crash loses the last change, which for this app is nothing. A bigger timer, say two seconds, saves more work and widens that window to something a user would notice. 150 is the founder's bet on where the line sits. Chapter 25 comes back to this as a performance tool.

WHERE TODAY'S ANALOGY BREAKS

Breaks when: you try to hand a recipe card to another recipe. In a kitchen you cannot pass carbonara as an ingredient. In JavaScript a function is itself a value, with a type, and it can be stored in a variable, put in an object, passed as an argument, and returned from another function. You already saw it in the Memento lane: the arrow function handed to addEventListener is never called by Memento's code, it is given away and called later by the browser. Real model: functions are values. A function passed to something else so it can be called later is a callback, and it is the backbone of every event and every network reply in the app. Chapter 12 takes that idea and builds the whole async story on it. A second, smaller break: the pile is not the only place a paused function can live. An await takes a card off the pile and puts it aside until the answer arrives, which is why the phone stays responsive while waiting on the AI. Also chapter 12.

RABBIT HOLE: what a stack overflow actually is

The pile has a size limit, a few thousand cards deep in most browsers. If a function calls itself with no way out, cards pile up until the limit, and the machine gives up with "Maximum call stack size exceeded". That message means one specific thing: something called something called something forever. It is the one error where the top of the stack trace is almost never the useful part, because the trace is the same three lines repeated a thousand times.
