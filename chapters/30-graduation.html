Quick check

Why is git add -A banned in Memento?
Two agents share one working folder. A blanket add stages their half-finished files along with yours and commits work nobody reviewed, which is how a duplicate feature ships. Name your files.
What does "APPROVED @ b6e148b2" actually approve?
That exact snapshot of the whole folder, identified by its fingerprint. Not the branch, not the idea. Change one character and the next commit has a different hash, so the approval visibly does not cover it.
You are told "the tests pass." What is missing?
The output. A claim with no evidence is a claim. Chapter 27's rule: if you cannot verify it, it did not happen. Ask for the summary lines, or run npm run check yourself in the lab.

The idea: the gate

Every serious codebase has a moment where reading stops and writing starts, and that moment is a permission, not a feeling.

Memento is under a code freeze. A freeze is a decision to stop changing something so that a second thing can catch up: here, the web app holds still at v1378 while the React Native rebuild chases it. A freeze is not laziness. It is how you stop the target moving while you copy it, and every change you allow through it is a change the other team has to replay by hand.

So this chapter has a gate in front of it, and the gate is one sentence from one person.

THE GATE. DO NOT PASS IT WITHOUT THIS

This chapter begins only when Malik has said, that day, in chat: "yes, do the graduation change on Memento." Not last week. Not implied by your being on chapter 30. Not an agent saying it is fine. Until that sentence exists the chapter is reading, and the lab from chapter 29 is where anything runs. After it exists, the agent adds an isolated worktree, a second working copy of the same repository on its own branch, and every change lives in there. The shared ~/Downloads/MEMENTO checkout is never switched, because another agent is standing in it. Nothing, ever, happens on main.

"(none yet)" is the proudest line in the repository: a freeze running since 11 September 2026 and nothing urgent enough to break it. If your change touches memento-app/, you write the first line in that file, and you had better be able to defend it.

Then the shipping rules, which you now read as git rather than as chores:

- **Before editing:** `git pull --rebase origin main` (get other agents' latest work).
- **After a meaningful change:** commit ONLY your own files: `git add <your specific files>
  && git commit -m "<what changed>" && git push origin main`. **NEVER `git add -A`**
- End commit messages with: `Co-Authored-By: ...`

Pull with rebase first so your work sits on top of theirs. Name your files so you commit only what you understand. Sign the message so the log says who wrote it. And where that quote says push to main, you do the safer version: push a branch and open a pull request, because a first change by a new engineer gets read before it merges. That reader is not you.

THE ALTERNATIVE, AND WHY MEMENTO CHOSE THIS

The alternative to a freeze is to keep shipping the web app while the native rebuild chases it. That is what most teams do, and it is why most rewrites die: the target keeps moving, the new version is never at parity, and one day somebody quietly gives up. The freeze costs real speed right now, and "(none yet)" is the receipt that it is being honoured. The alternative to a pull request for your change is to push straight to main, which the rules file literally permits for the agents. You are not taking that permission, because the cost of a bad first commit on a live app is not measured in time.

The change

Small. Real. Yours. The freeze picks the shape: on the web side, only a bug fix that blocks a real person or a test account, logged in FREEZE-LOG.md. On the native side there is no freeze, so a small typed change with a test next to it is fair game. Either way the rule is the one that governs your agents: one thing, named, understood end to end.

The safe shape, in order:

  1. Read the plan, out loud, before any file opens. One sentence: what changes, in which file, and how you will know it worked.
  2. git -C ~/Downloads/MEMENTO pull --rebase origin main, then make the worktree: git -C ~/Downloads/MEMENTO worktree add ~/Downloads/CODE-BOOK/lab/graduation -b grad/<short-name>. That creates the branch and a separate folder to work in, and leaves the Downloads checkout exactly where it was. Everything after this happens inside ~/Downloads/CODE-BOOK/lab/graduation.
  3. Make the change. Read the diff line by line, chapter 27 style, including the lines you did not expect to see.
  4. Verify inside the worktree, never in the chapter 29 lab copy, which is pinned to an old snapshot and would test the wrong code. Native: npm run check in ~/Downloads/CODE-BOOK/lab/graduation/memento-native. Web: the console gate, zero errors, and the four-cell screenshot matrix if anything visual moved.
  5. Commit the named files with a message that says what changed and why, ending with the co-author line the rules file requires.
  6. Push the branch and open the pull request: gh pr create, or the button GitHub shows you after a push.
  7. Stop. The chapter ends at a reviewed branch. Merging is a separate yes, from the same person, on a different day if he wants.

WORDS YOU NOW OWN
Code freeze
A deliberate stop on changes to one part of a system so something else can catch up. Enforced by a written rule, not by hope, and every exception is logged.
Code review
Somebody who did not write the change reads it before it merges. In Memento the reviewer is the other agent, and the approval is pinned to a commit hash.
Pull request (upgraded)
A page holding one branch, its commits, its diff, its test results and its review. The place a change waits, visible, until someone with authority merges it.
Evidence
Command output, a test summary, or a screenshot of the real surface. Anything else is a claim, including one from you.
WHERE TODAY'S ANALOGY BREAKS

Breaks when: you imagine the range goes cold by itself. It does not. A branch sits there live until it is merged or deleted, a pull request can rot for months, and a half-finished branch is the commonest way a codebase acquires a ghost. Also, a range officer sees every shooter. Malik cannot see what an agent did at 3am unless it is in the log, which is why the rules make the repository the record. Real model: permission is a decision with a timestamp and a scope, and it expires. Written down it survives. Remembered, it does not.

RABBIT HOLE: what a real team bolts onto this

Everything in this chapter is enforced by people remembering. Teams replace that with machinery: branch protection that makes main refuse a direct push, required status checks so a pull request cannot merge while the tests are red, required reviewers per folder via a CODEOWNERS file, signed commits, and a changelog generated from commit messages. Each one turns a rule you have to remember into a rule that enforces itself, and each one costs setup time and a little speed. Memento has almost none of it, deliberately, because the two contributors are agents that cannot click a merge button. The day a second human touches this code, that stops being the right trade.
